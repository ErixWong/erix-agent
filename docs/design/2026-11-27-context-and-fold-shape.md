## 0. 目标与边界

折叠只有一个目的：**在预算内，让模型仍然能做对下一步决定。**

不是"保存历史"（账本负责），不是"压缩率"（那是手段）。

由此得到唯一的分拣判据：

| 信息 | 去哪 |
|---|---|
| 模型下一步需要、而它**自己拿不到**的 | 进上下文（白板 / 折叠日志） |
| 模型**能自取**的（文件内容、历史细节、命令输出） | 留在账本，按需查 |
| **不变的**（项目规矩、常量、常识） | 项目指令，不进折叠 |
| **会变的现状**（待办、约束、教训） | 白板（`runs.board`，一整块文本），整块覆盖写 |
| **这一段发生了什么** | 折叠日志，只追加 |

时间维度的划分是这套形状的骨架：**白板是现在时，折叠日志是过去时，项目指令是无时态，账本是全部时态。**

## 1. 表

> **表的划分依据是读者集合，不是数据的相似性。** 两张表该不该合并，看"谁读它"：
> `messages` 的读者是渲染 / 折叠 / token 估算 / resume；`notes` 的读者是 note 工具与目录渲染。
> **白板不读 `notes`**——它是 `runs.board` 一列（§1.7 说为什么）。
> 读者集合不相交就不合表——合表等于让多个读者替一个读者的需求买单（每个都要带白名单），
> 而 `messages` 会重新长成 tag-union。
>
> 反过来说：如果一条事实**只有**某一类读者，它就该独立成表，哪怕每行只有 3 列。
>
> **事实表 vs 事件表，主键不同**：
>
> | | 事实表 | 事件表 |
> |---|---|---|
> | 主键 | **对象身份**（如 `tool_use_id`） | **事件序号** |
> | 同一对象 | 最多一行，重复写幂等 | 可以多行，每次都是新行 |
> | 回答 | "它现在是什么状态" | "先后发生过什么" |
>
> 本形状里没有通用 `events(type, payload jsonb)` 表：那是无类型、无约束的黑洞，
> 而且会诱导"同一件事发生两次"变成合法数据。每类事件都有它自己的**事实表**
> （`folds` / `notes.superseded` / `runs.termination_reason` / `judge.log`），列与读者各自明确。

### 1.1 `runs` —— 会话（session）

> **`runs` 就是 session。** 表名与列名保留 `runs` / `run_id`，是因为公开面（契约、事件、宿主代码）
> 早已这么叫；**语义上它就是会话**，本文正文一律写"会话"。

**一行 = 一个 `runId` = 一个会话（session）。** CLI 的 `--session <id>` 就是它
（`runId = options.session ?? 默认 id`），resume / `-c` 续的是同一个 id，所以也是同一个文件、同一行。

⚠ **`run` 这个词在代码里被用成两个意思**，别混：

| 说 "run" 时指 | 是不是一行 |
|---|---|
| 会话（`runId`） | **是**，就是本表一行 |
| 一次 `runToolLoop` 调用 | **不是**。它只是往这个会话里追加轮次；`runRounds`（本次调用消耗的轮数，resume 后从 0 重算）是它的派生计数，不是实体 |

第二条不建模：它没有独立的生命周期，也没有读者需要那个边界（成本归因查 `llm_call` 按轮聚合就够）。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK** | 跨 resume 不变 |
| `termination_reason` | text | 可空 | **怎么结束的**：`end_turn` / `judge_done` / `no_tool` / `stall` / `max_rounds_cap` / `aborted` / `failed` / `persistence_failed`。**`NULL` = 没结束**（在飞，或崩了）——收口与否由它表达，不另立 `status` |
| `termination_detail` | text | 可空 | 一句人可读说明。**读者是宿主 UI**（引擎内零读）——错误文本没有第二个家：返回对象宿主不落盘就没了 |
| `termination_error_code` | text | 可空 | 仅 `reason='failed'` 时：`timeout` / `rate_limited` / `auth` / `unknown` |
| `state_version` | int | not null | **状态块注入过几次**。计数器，不可派生 |
| `low_budget_prompted` | boolean | not null default false | **防重复**：低预算提示已经给过 |
| `guard_extension_used` | boolean | not null default false | **防重复**：扩轮额度已经领过 |
| `context_recovery_used` | boolean | not null default false | **防重复**：上下文超窗恢复额度已经领过 |
| `store_folds_channel_absent` | boolean | not null default false | **降级事实**：store 没实现折叠通道（`appendFold` / `loadFolds`） |
| `store_folds_channel_write_failed` | boolean | not null default false | **降级事实**：这次折叠写不成（与上一条不是同一件事：「宿主没实现」vs「写失败」） |
| `max_rounds` | int | | 本次运行的轮数预算（输入配置） |
| `verification_status` | text | 可空 | **验证结论**：`verified` / `unverified` / `skipped` / `error`。**不可派生**——guard 真的跑过才有这个值 |
| `verification_reason` | text | 可空 | `deliverables_failed` / `machine_only` / guard 给的 reason |
| `board` | text | | **白板：一整块现状文本**（≤1500 token），整块覆盖写。不是表——渲染时整块拼进上下文，没有按条目查询的读者（§1.7） |
| `created_at` / `updated_at` | timestamptz | not null | 保留期与审计的信封。**今天代码里没有 run 级时间戳**（只有轮记录的 `ts`），是形状要求 |

**为什么没有 `status`**：一个 `status` 列曾把三个维度压成一个有损投影——

| 维度 | 事实住哪 | 压进 `status` 的后果 |
|---|---|---|
| 收口了没有 | `termination_reason IS NULL` | 变成 `running`（和"在飞"分不开） |
| 怎么结束的 | `termination_reason` | 和验证结论混成一格 |
| **验证结论** | `verification_status` + `verification_reason` | `verified` 与 `skipped` 都变 `succeeded`；`deliverables_failed` / `machine_only` 整个消失 |

前两个可派生，**第三个不可派生**（guard 跑没跑过不是任何字段的函数）。所以 `status` 删掉，三个维度各自成列：
清理判据读 `termination_reason`，UI 读 `verification_status`，审计读 `verification_reason`，各读各的，没有"同一个派生表达式必须写在一处"的纪律要求。

`guardVerdict` / `guardMetrics` 是诊断面（宿主调试用），进 `compaction_stats` 之外的诊断位——**不占列**。

**为什么 `state_schema_version` / `state_epoch` 不是列**：它们是快照里的 `schemaVersion` / `stateVersion`。
一个事实只住一处——列和 jsonb 各存一份，就多了一条"必须同步"的纪律，而没有读者需要按它们查询。
快照里的 `stateVersion` 数的是**注入次数**，不是版本号（这个名字会被所有人读错，但它住在快照 schema 里，
名字由那边决定）。

**这五个「一次性事实」是列，不是 jsonb**：它们原来住在 `state.deterministic` 里，用**键不存在**表示
「没发生过」。换成 `default false` 的列之后：① 「缺席 vs false」的歧义消失；② 可以直接查
（「哪些 run 用过扩轮额度」不必扫 jsonb）。给它们起一个容器名（`quotas` 之类）只是把删掉的 jsonb
换个壳——读者看到的仍是不透明 blob。

**没有 `state` 这个 jsonb**：它原来装 12 个键，实测 90 份真实快照里——

| 键 | 非默认值的快照 | 能不能算出来 |
|---|---|---|
| `tools` 非空 | 51（57%） | **能**（数 `tool_use` 块） |
| `stateVersion > 0` | 28（31%） | 不能（计数器）→ 列 |
| `filesWritten` 非空 | 19（21%） | **能**（扫写工具入参） |
| `foldedRounds > 0` | 10（11%） | **能**（`max(cut_round)`） |
| `lowBudgetPrompted` | 8（9%） | 不能（决定）→ `quotas` |
| `compactionStats` 非空 | 1（1%） | 不能（实测）→ 列 |
| `semantic` / `errors` / `guardExtension` / `contextWindowRecovery` | **0** | 能 / 能 / 决定 / 决定 |
| `rendered` | 每次保存都写 | **纯投影，写进去再没人读**：全仓 3 处读点全读内存对象，`resume` 直接重渲染（`resume-manager.js` / `run-state.js` 里 grep `rendered` 零命中） |
| `stateStatus` / `stateAvailability` | 恒 `available` | **读者对快照的观测，被写进作者的产物**——能不能用是读的时候判的 |

**热路径在内存，不在表上**：引擎每轮渲染读的是增量维护的计数器；`tools` / `filesWritten` / `foldedRounds`
这类统计要重建时，一次 `GROUP BY` / `jsonb_array_elements` 扫描就够，而 `resume` 本来就要把全部消息读进来。


### 1.2 `rounds` —— 一行一轮（元数据）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK₁**, FK→runs | |
| `round_no` | int | **PK₂** | ≥ 0；`0` 是 seed |
| `provider_stop_reason` | text | | **provider 给的结束原因**：`tool_use` / `end_turn` / `max_tokens`。**不是「本轮为什么停」**——那是 `runs.termination_reason`。实测 906 轮只有前两个值，且与「本轮有没有工具调用」完全相关；`max_tokens` 是续写门的输入（读的是内存里的 response，不是这一列） |
| `usage` | jsonb | | 本轮**累计**用量（截断续写时是多次之和） |
| `response_usage` | jsonb | | **最后一发的原始 provider usage**。实测 25 轮里 13 轮与 `usage` 完全相等、12 轮只差 `reasoningTokens`——它不是「另一个事实」，是 `usage` 的桶里没有的 provider 特有字段（`bin/reasoning-effort.js` 读它做推理强度校准） |
| `engine_usage` | jsonb | 可空 | **本轮引擎自发起的调用**（round judge / 收尾归一化 / 折叠摘要）的用量。缺键 = 本轮没有这类调用。`usage` 只装主模型桶——只留 `usage` 会把引擎用量藏进主账 |
| `wrapup` | jsonb | | 收尾那一次的结构化产物（**真状态**：模型输出的规范化结果，不可重算）。只有最后一轮有值 |

**没有 `status` / `started_at` / `closed_at`**：它们是 append-only 文件的补丁，不是业务事实。

| 字段 | JSONL 里为什么需要 | 关系模型里为什么不需要 |
|---|---|---|
| `status` | 先追加轮行再追加消息行，崩溃可能只写半行 | 轮行与消息**同一事务**提交，不存在半行 |
| `started_at` | 记「什么时候开的」 | 上一轮的 `ts` 就是本轮的 start |
| `closed_at` | 记「什么时候收的口」 | 就是本轮的 `ts` |

而「崩溃在轮中」这个业务事实，**消息层已经看得见**：有 `tool_use` 没有对应 `tool_result` = 那一轮没跑完。
§3.9 的折叠闸门判的就是它。`status='open'` 不提供任何消息层拿不到的信息。

**没有 `summary`（单轮自述）**：生产者协议（`<erix-summary>` 内联标记）**在任何提示词里都不存在**
⇒ 实测 1,021 轮里 885 轮是兜底串 `"missing"`。三个读点，一个都不受益：

| 读点 | 读到什么 |
|---|---|
| `governorState.runningLog` | 只被裁剪器读（决定丢哪条），从不渲染 |
| `bin/display/projection.js` | CLI 投影的 `meta.summary` 标签——`bin/` 是调试面，不是契约面 |
| `src/compact/fold-statistical.js` | 折叠统计策略的摘要回退：`record.summary.trim()`。`"missing"` 是**非空字符串**，于是兜底串被当成摘要写进折叠段 |

judge 的「时间线」来自 `buildTimeline(messages)`，与它无关。要保证质量就得每轮多一次 LLM 调用，
而**当前上下文里没有它的读者**——所以先删，要的时候再加。按轮标签今天能现算（过滤本轮
`caller='assistant'` 的 `text` 块拼接）。

**没有 `l0facts`**：98.7% 的行存的是 `{exitOk:true}`——它认的失败口径是「工具抛异常」（`is_error`），
而真实失败是「命令退出码非 0」，两者在 1,021 轮实测里几乎不相交（`is_error` 只在一个合成 fixture 里出现）。
它的两个消费者（judge 的「最近错误」、resume 的 `errorRepeat` 重建）在实测里都是空转，而活着的重复错误
守卫本来就从 `messages` 现算、不读这一列。留下的只有 `errorText` 那份 500 字原文副本，违反不变量 #1。

**没有 `tool_use_count`**：能从 `messages` 数出本轮 `tool_use` 块。唯一读者是
`bin/display/projection.js` 的投影（调试面），引擎内部零读。

**没有 `text_preview`**：它是"过滤本轮 `caller='assistant'` 的 `text` 块再拼接"——一条 `GROUP BY` 就能算。
缓存列的不一致风险是实的（消息补写了、预览不更新，两边对不上时你不知道信谁）。

**轮行与消息同一事务落盘**：不存在「半行」。崩溃的形状是「这一轮没有行」，而「轮跑到一半」的证据在
消息层——悬空的 `tool_use`（没有对应 `tool_result`），§3.9 的闸门判它。

### 1.3 `messages` —— 一行一条消息

消息是**最小单位**。每条消息属于且只属于一轮。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK₁** | |
| `round_no` | int | **PK₂**, FK→rounds | 它属于哪一轮 |
| `msg_seq` | int | **PK₃** | 轮内单调，从 0 起 |
| `caller` | text | not null | **谁写的**：`user` / `assistant` / `tool` / `judge` / `engine` |
| `role` | text | not null | **协议要求它装成谁**：`user` / `assistant` / `system` |
| `part_of_msg_seq` | int | 可空，自引用 | **切片归属**：这条是某条逻辑消息的一个分片，指向**首片** |
| `content` | jsonb | not null | 块数组（`text` / `tool_use` / `tool_result` / `image`），保序 |
| `ts` | timestamptz | | 信封时刻（不是顺序依据） |

**没有 `dedup_key` / `payload_fingerprint`**：两个都是 JSONL 的产物。

| 字段 | 今天是什么 | 关系模型里为什么不需要 |
|---|---|---|
| `dedup_key` | `<runId>:msg:<round>:<seq>` 这类字符串 | **就是复合主键的字符串编码**——主键已经承担幂等身份 |
| `payload_fingerprint` | 整行 payload 的 `sha256[:24]` | 一行是不透明 blob 时才需要哈希比内容；关系模型里「同一份 payload」就是**非主键列全相等**，精确比较。存成列还会自指（行里存着这一行的摘要），任何字段变了都要重算 |

**`role` 为什么留着（虽然它是 `caller` 的函数）**：因为它记的是**决定**，不是投影。
引擎在组装请求时决定这一条装成谁；重算等于用**今天的映射规则**重新解释**当时的决定**——
规则一变（例如引擎注入改用 `system`），历史行就被读成另一件事。而且 `role` 属于 §2 说的
「实际喂给模型的那串字节」：渲染时重算，渲染结果就可能与当时真正发出去的不一致。
（今天的映射是满的——`role='system'` 只出现在请求组装里，从不落盘——所以「今天重算」不会错；
风险全在规则变更与「渲染/发送两份实现」这两处，而那正是这份文档要消灭的东西。）

**`caller` 与 `role` 是两个维度，别合并**：

| `caller` | 是什么 | `role` |
|---|---|---|
| `user` | 人 / 宿主提问（`steer` 也走这里） | user |
| `assistant` | 模型返回（可同时带 text 和 tool_use） | assistant |
| **`tool`** | **工具结果** | **user** ← 协议把它塞进 user 消息，但作者不是用户 |
| `judge` | **judge 模型的评审意见**（引擎只是转述） | user |
| `engine` | 引擎自己的模板注入（“已到预算上限，请收尾” / guard revise） | user |

一致性约束：`caller='tool'` ⇔ 含 `tool_result` 块；`caller='assistant'` 可含 `tool_use` 块；
`caller='user'` 只含 text（提问）；`caller IN ('judge','engine')` 不含 `tool_result`。

**顺序从自然键推出来，不需要全局序号**：

| 要排什么 | 用什么 |
|---|---|
| 轮内消息 | `msg_seq` |
| 跨轮 | `round_no` |
| 折叠之间 | `folds.seq`（§1.4） |

全局 `seq` 是**单文件 JSONL 的产物**（一个文件里没有类型，只有行序）。拆成表之后，行序由自然键承担，
`ts` 只作记录、不作顺序依据（墙钟会回拨，同一毫秒还可能有多条）。

**序号由写入方分配，不是存储自增**——这条是形状级的，不是实现细节：

| | |
|---|---|
| 谁给号 | **引擎**（`nextMessageSeqByRound` 从已落盘行播种，轮内递增；折叠序同理） |
| 存储做什么 | 只持久化 + 提供播种用的读数 |
| 为什么不能用自增列 | 崩溃重跑必须拿到**同一个号**；存储自增每次都给新号，而"同一条消息换号"在账本上就是**同 key 异 payload = 冲突** |
| 代价 | 零：JSONL / 内存 / SQLite 三种存储一视同仁，不需要任何存储特性 |

顺带一条：Node 22+ 内置 `node:sqlite`（本机 v22 可用，带 ExperimentalWarning），所以"CLI 自建 SQLite"
在零依赖红线内是可行的。但它是**宿主的一种可选实现**，不是形状的一部分——形状只要求"能按自然键排序"。

**哪些消息进折叠**：`caller IN ('assistant','tool')`。`user` 不进——宿主的幂等判据要求
`load()` 能看见自己那条 `dedup_key`；`engine` 不进——它在轮记录落盘之后才产生。

**切片（`part_of_msg_seq`）—— 一行一条消息，但一条消息可以是多行**：

模型一次调 3 个工具，结果**每完成一个就落一行**（崩溃时不丢已完成的），靠 `part_of_msg_seq` 标
"我属于同一条逻辑消息"：

```
msg_seq=0  assistant  [text, tool_use(tu_1), tool_use(tu_2), tool_use(tu_3)]   ← 首片
msg_seq=1  tool       [tool_result(tu_1)]   part_of=null                        ← 首片
msg_seq=2  tool       [tool_result(tu_2)]   part_of=1
msg_seq=3  tool       [tool_result(tu_3)]   part_of=1
```

**折叠与渲染必须拼回一条**：协议要求一条 `tool_use` 由**紧随其后的那一条** user 消息结清；
拆成三条 user 消息发出去，provider 直接 400。

⚠ **`part_of` 只能指首片，不许链式指上一片**。链式会让"每隔一片落一次"（首片 → 指向它 →
指向分片），配对永久失败，而且坏形状是**静默的**：不报错、不丢块，只是工具结果再也配不上。

**“段”（人的一次提问 → 它引发的所有轮）是一条查询**：按 `caller='user'` 的消息切，不建表。

### 1.4 `folds` —— 一次折叠 = 一行

**折叠的产物不是一份累计文档，而是一条局部日志。** 旧行一个字都不改。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` / `seq` | text / bigint | **PK(run_id, seq)** | `seq` = 会话内严格递增折叠序 |
| `cut_round` / `cut_msg_seq` | int | not null | **切点**：这一折吃掉了「≤ 此切点」的全部消息 |
| `prior_seq` | bigint | FK→folds(run_id, seq)，可空 | 续写基底 = 上一折。**用外键，不用哈希** |
| `title` | text | not null | **模型写的短标题**，≤ 60 字符 |
| `title_src` | text | not null | `model` / `first_line`（回退，见 §3.4 ①） |
| `description` | text | not null | **模型写的三节**（行动 / 遗留 / 关键词），约 400 token |
| `tokens_before` / `tokens_after` | int | not null | 折叠前后的上下文 token。**每折省了多少就挂在折上**——不需要另立一张压缩统计表 |
| `intent` | jsonb | not null | **折叠前的白板全文**（机械抄）——渲染成 `## 意图` |
| `commits` | jsonb | 可空 | 这一折的 commit（`[{sha, subject}]`，机械抓）——渲染成 `## 提交`；抓不到就空 |
| `source` | text | not null | `llm` / `host`。**没有 `statistical`，也没有 `mechanical`**：后者今天存在，专指「LLM 摘要失败后的降级」；本形状里解析不出就是**折叠失败**（§3.7），不降级 |
| `trigger` | text | not null | `budget` / `context_window_recovery` / `manual` |
| `superseded_by` | bigint | 可空，FK→folds(run_id, seq) | 被后来的某一折取代。**只加指针，不改行**。读者是**渲染**：被取代的折不渲染——否则恢复后重折的那一段会出现两次（旧折描述半段、新折描述整段） |
| `created_at` | timestamptz | not null | |

**代码里有、形状里故意没有的四样**（不写清楚就会被当成遗漏，下次有人补回来）：

| 代码里的字段 | 被什么取代 |
|---|---|
| `toolCalls: [{name, argsSummary}]`（每折的工具足迹） | `description` 的 `## 行动`——模型写的比机械足迹有用 |
| `bytes` / `bytesBefore` / `truncated` | `tokens_before` / `tokens_after`——序列化尺子 vs 预算尺子，只留后者 |
| `degradeReason` | 不降级：解析不出就是折叠失败 |
| `fingerprint` | 折叠身份改用三元组 `(cut_round, cut_msg_seq, prior_seq)` |

**没有 `compaction_stats`**：今天的六层压缩里只有 `foldLlm` 是折叠——`slidingWindow` 是**整轮丢弃**
（新形状里被梯度渲染取代，内容不丢）、`foldStatistical` 新形状里没有、`anchors` 是折叠的附属产物、
`ttl` 与 `enforceSize` 是安全网。**新形状里唯一的压缩就是折叠**，所以省下的 token 记在折上，
不另立事件表。

**没有 `description_tokens`**：`estimateTokens(description)` 对 ≤4000 字符是微秒级，每轮最多算 10 折；
而这一列连代码里的读点都没有。缓存列的不一致风险（换 tokenizer 就过期）是实的。

**折叠的身份是三元组** `(cut_round, cut_msg_seq, prior_seq)`：切到同一个点先后两次折（恢复前 `prior_seq=NULL`、
恢复后 `prior_seq=3`）是**两次折叠**，不是一次。哈希身份是为"没有行 id 的存储"发明的，有了主键就没有理由。

**没有 `stage_no`**：分组是渲染时现算的（§1.6），不在行上。

**没有 `text`（累计体）**：累计体每折被重写一次，同一段内容会被压缩两遍、三遍（§5 有实测）。

### 1.5 折叠的成员是**推导的**，不建表

折叠永远从最老的往前吃一段**前缀**，所以只需要一个**切点**，不需要成员表，也不需要例外表：

```sql
-- 这一折吃掉了什么：所有 (round_no, msg_seq) ≤ 切点的消息
SELECT * FROM messages
 WHERE run_id = ?
   AND (round_no, msg_seq) <= (?, ?);
```

| 为什么不需要例外 | |
|---|---|
| 折叠之后才追加到已折轮里的消息 | 它的 `(round_no, msg_seq)` **天然 > 切点** ⇒ 自动不算被折 |
| 被安全层删掉的消息 | 那属于"离开上下文"的另一个问题，不是"被折走" |
| 字节上限夹断 | 那是 `description` 自己的预算（§3），与成员无关 |

**原文一条都不复制**：被折走的正文只在 `messages` 里存一份。

实测依据：一份真机归档里，被归档的副本 940,278 字节，而它拷贝的那些行自己合计 941,379 字节
——**差 0.1%，等于纯冗余**。

### 1.6 两样东西是渲染时算的，**不是表**

#### ① 分组行

折数一多，`title` 也是线性增长的（1000 折 × 20 token = 20k）。需要把最老的那些并成一行——
但这件事**不需要存储**：

> 按 `seq` 每 10 折一组，渲染时现算。组标签 = `第 a–b 折 · <组内第一折（跳过已作废的）的 title>`。

三点理由：

1. **它是纯函数**：`folds` 行只追加不改，所以每 10 折的边界永远不变，现算结果与存下来逐字相同。
2. **它不需要 LLM**：标签直接用组内第一折的 title（那本来就是模型写的）。存表就得另外调一次模型起名，
   多一份预算、多一条失败路径。
3. **它没有生命周期**：存表就要回答“新折进来要不要重分组”“旧组要不要作废”——现算不产生这种问题。

代价是标签质量略差（组内第一折的标题不一定概括整段）。可以接受：这一层是**回忆的指针**，
不是摘要——真要细节就去查账本。

#### ② 会话级概述

“这段会话到底干了什么”——宿主横幅与人类阅读都要它，但**也不要存**：

```sql
SELECT seq, title FROM folds
 WHERE run_id = ? AND superseded_by IS NULL ORDER BY seq;
```

拼出来就是概述；超过一定条数会自动并成分组行（①），再想细就拼 `description`。

**不存理由**：它是上面这些行的函数。一旦落进 `folds` 行（每折一份）就是 N 份越来越大的
累计快照——这正是被否掉的那个形状（实测摘要 3.9k → 5.9k → 6.9k token，涨的全是重复）。
即使只存“最新一份”，那也是一次**不可审计的重写**：模型每折压一遍，丢掉了什么账本上看不出来，
而它能提供的信息量，十条 title 已经给了。

### 1.7 `notes` —— 小抄本

**白板不在这张表里。** 它是 `runs.board` 一列（§1.1）。理由是两个读者集合不相交：

| | `notes`（小抄） | 白板（`runs.board`） |
|---|---|---|
| 读者 | 模型**主动**查（`note_read`） | 渲染器**每轮**拼进去 |
| 时机 | 按需 | 无条件 |
| 大小 | 100–4000 字一条 | ≤1500 token 一整块 |
| 生命周期 | 有保留期，会过期 | 不过期 |
| 形态 | 一条一条，有 `key` | 一块文本，无内部结构 |

一个 `pinned` 标记曾想把两者绑在一张表里。实测零可观测效果（§6），已删。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK₁** | |
| `key` | text | **PK₂** | 稳定标识：≤24 字符，`[a-z0-9-]`。**不是标题**——改标题不该换笔记 |
| `title` | text | not null, ≤60 | 目录显示的那一行。写侧上限 = 显示上限，否则模型写的后半截永远看不到 |
| `content` | text | not null, ≤4000 | 正文 |
| `superseded` | jsonb | not null | **版本栈**：被覆盖掉的历史版本，最多 3 条（`MAX_SUPERSEDED`），最近的在最前。契约面：数组顺序是值的一部分 |
| `state` | text | not null | `active` / `revoked` |
| `created_at` / `updated_at` | timestamptz | not null | 保留期只看 `updated_at`。`created_at` 的读者是**审计**（「这条事实什么时候第一次记下」）——它**不可派生**：一旦更新过，创建时间就再也算不回来，所以它不适用「能算出来的不进列」 |

**没有 `kind` / `pinned` / `board` / `tags` / `relevance`**：

| 删掉的 | 理由 |
|---|---|
| `kind` | 五个值（约束/待办/教训/事实/阶段）全是白板的分类，白板一走只剩单值 |
| `pinned` / `board` | 白板的开关，随白板一起走 |
| `tags` | 目录不渲染它 ⇒ 在"要不要读"的决策点上不可见 ⇒ 无法可靠使用 |
| `relevance` | 模型自评的相关度，没有客观依据 |
| `author` / `provenance` | `auto` 在 `src/` 里只有读者、没有生产者；目录渲染的 `@agent` 恒为常量，`note_list` 的 `source` 过滤连工具面都没暴露 |

**没有 `current` JSONB**：`title` 有专门读者（目录渲染）和长度约束，JSONB 里只能靠触发器；
`content` 是正文。两者都不需要"任意扩展"。

**历史就是 `superseded`（行内，≤3 版），不另立事件表**。唯一的读者是 `note_read` 返回给模型的
"已作废条目，不得当作当前值使用"——它要的是**以前的值**，不是"谁在何时改了什么"。
一个 `note_ops(before, after, op, ts, fold_seq)` 事件表被设计过又删掉了：`after` 就是当前行、
`ts` 就是 `updated_at`、`revoke` 已由 `state` 表达、`fold_seq` 在白板改成一块文本之后没有来源。

**发现面只有一个：`note_list`**

| 面 | 返回什么 |
|---|---|
| 自动注入 | **不注入正文**；只在有证据时给一句"先用 `note_list` 查找"（`note-prompt-hint.js` 的证据门） |
| `note_list` | 全部 `active` 的 `key` + `title`，按 `updated_at` 倒序 |
| `note_read` | 按 `key` 取全文 |

**目录里必须同时给 `key` 和 `title`**：`title` 是"要不要读"的判断依据，`key` 是取回的句柄。
只给标题，模型知道有这么个东西却取不回来（标题会重复、会改，key 不会）。

**目录为空时不注入**——否则每轮都在告诉模型"你没有小抄"。

### 1.8 关系总图

```
runs 1─┬─N rounds ──── N messages（最小单位，轮内按 msg_seq 排）
       │                     ↑
       │            切点 (cut_round, cut_msg_seq)：折走的就是「≤ 切点」那一段
       ├─N folds ───────────┘   （成员是查询出来的，不建成员表）
       │    └─ N:1 folds（prior_seq = 续写基底）
       ├─1 board（一列文本，不是表）
       └─N notes（含 superseded 版本栈）
```

**五张表**：`runs` / `rounds` / `messages` / `folds` / `notes`。
没有 `fold_exclusions`（切点推导）、没有 `tool_executions`（恢复不猜状态）、没有 `budget_verdict`
（`runs.termination_detail` 一列）、没有 `stages` / `segments` / `vector`（都是渲染时算的）。

## 2. 事实归属：什么东西住哪里

同一个名字在账本里可能有四个不同的东西，混起来就会"恢复两遍"或"挤掉真相"：

| 东西 | 真实身份 | 归属 |
|---|---|---|
| `folds.title` / `folds.description` / `folds.intent` | **折叠事实**（本折日志） | `folds` |
| 实际喂给模型的那串字节 | **请求事实**。今天字段名有两个，别混：`foldedSummary.text` 是折叠后**整条消息**的投影（含原任务正文与安全层插的 `[已修剪]`）；`foldedSummary.fedSummaryText` 才是「写侧当场证得的那一块」逐字副本 | 留在**该轮的记录**上，不从 `folds` 派生 |
| `requestStateBlock` | 会话状态块的渲染 | **派生**（从 `rounds` + `folds` + `notes` 现拼），不落正文 |
| 白板（`runs.board`）vs `notes` | **现状 vs 可查存档**：白板每轮整块注入、整块替换；`notes` 一条一条，按需 `note_read` | `runs.board` / `notes`，不互相派生 |
| **judge 决策**（done / confidence / reason / evidence / direction） | **控制流证据**，不进上下文、不参与渲染 | **外部账**：`judge.log`，按 `runId` join。形状只收它**注入的那条消息**（`caller='judge'`） |
| `foldedPayload` | 被折走的原始消息 | **派生**（§1.5 的切点查询），不落正文 |
| `compactionStats[].foldSummary` | 指标 | 诊断面，只放信号 |

**写点后移**：喂给模型的那串字节要在**请求组装处**（所有压缩层定稿之后）写。于是它记的就是"模型真正
看到的那一串"，不再需要「钉住块对象身份 + 自证」。

## 3. 上下文组装

### 3.1 四层

```
┌────────────────────────────────────────────┐
│ 系统提示        固定（项目指令、常量、规矩）    │
├────────────────────────────────────────────┤
│ 遥远的回忆      只留 title，按轮次升序          │
├────────────────────────────────────────────┤
│ 详细日志        title + description，按轮次升序 │
├────────────────────────────────────────────┤
│ 白板            runs.board 一整块（约束/待办/教训/事实）│
├────────────────────────────────────────────┤
│ 活跃保留区      最近 K token 的原始消息          │
└────────────────────────────────────────────┘
```

**关键性质：不重写。** 每次折叠只追加一条 `folds` 行；旧行一个字不动。所谓"渐变"是
**对同一批日志按预算做梯度渲染**，不是"再摘要一次"。

### 3.2 渲染算法（确定性，零 LLM）

```
B = 窗口 × 2.5%                       ← 历史层预算（白板另算）
从最新一折往回：
  ① 60% B 给 description（每条 ≤ 500 token）
  ② 30% B 给 title（每条 ≤ 20 token）
  ③ 剩下给分组行（每 10 折一组，现算：`第 a–b 折 · <组内第一折的 title>`）
```

同一批记录 + 同一个预算 ⇒ 同一输出。**纯时间序，没有相关度排序**——原因见 §6。

### 3.3 预算

| 用途 | 200k 窗口 | 512k 窗口 |
|---|---|---|
| 白板（固定 **1500 token ≈ 1000 汉字**，不随窗口缩放） | 1.5k | 1.5k |
| 详细日志（60% B） | 3.0k | 7.7k |
| 遥远的回忆（30% B） | 1.5k | 3.8k |
| 分组行（10% B） | 0.5k | 1.3k |
| **历史层合计（B = 2.5%）** | **5.0k** | **12.8k** |
| **白板 + 历史层** | **6.5k（3.3%）** | **14.3k（2.8%）** |
| 活跃保留区（4%） | 8k | 20k |
| 余量 | 16k | 16k |

白板**不跟着窗口缩放**：它的大小由"必须一直在的东西有多少"决定。窗口小的时候宁可少放几条日志，
不少放一条约束。

### 3.4 四条硬前提（缺一条这套就塌）

1. **`title` 必须是模型写的短标题。** 回退到"正文首行"的记录做不了"遥远的回忆"——它不是标题。
   回退必须留 `title_src='first_line'`，且这种记录**不进第一层**。
2. **`description` 必须自解释。** 每条会被单独拿出来按轮次排列，脱离上下文读。出现"上面 / 刚才 /
   该文件 / 前面提到"这类指代即不合规。
3. **每一折必须能单独编码。** 这是形状对"跨库检索"的唯一承诺：`description` 拎出来（配 `title`
   与 `(run_id, seq)`）就足够让任何人算出一条可用的向量，不需要同一会话的其它行、不需要原任务。
   做不到这一条，检索层就永远得把整个会话塞进去才能判断相关度。
4. **必须有分组行。** 否则 `title` 数量线性增长（§1.6）。

### 3.5 渲染的边界与退化

| 情况 | 行为 |
|---|---|
| 估算与真实 tokenizer 不一致 | 按 **0.9B** 渲染；provider 报超窗 ⇒ 记一行 `budget_verdict`、**降一档重试一次** |
| 窗口极小（装不下一条 description + 一条 title） | 降级顺序：最新一条 description → 只给 title → 只给阶段线 |
| 连一条分组行都装不下 | **`cannot_fit` 显式失败**。不许静默只给保留区——模型会以为自己是从头开始的 |
| 任何一档装不下整条 | **降档，不夹断**。半条 description 比没有更坏：模型会补全不存在的细节 |

**永远不出现"零历史"**：至少留一条分组行，让模型知道"你看到的历史是被折过的"。

### 3.6 白板与日志的分界

| 说的是 | 住哪 |
|---|---|
| "现在是什么"（约束、待办、已知的坑、当前阶段） | 白板 |
| "这一折发生了什么"（做了什么、结果如何、为什么这么改） | 日志 |

两处都写的后果不是浪费 token，是模型读到**两份略有出入的版本**，然后按其中一份行动。

这条边界靠 prompt 约束 + 人工评审守，**不做脚本闸**——措辞类判定写 `if/else` 只会把注意力换成改常量。

### 3.7 折叠时一次调用产出三件事

1. `description`（本折日志）
2. `title`（短标题）
3. **新白板全文**（整块，≤1500 token）

分开调用是两次付费、两次延迟，而且第二次看不到第一次的输入。

**白板是整块替换，不是增量指令**：模型交回的就是下一版的全文，引擎只校验长度然后整块覆盖。
没有 `add` / `update` / `drop`，也就没有"某条被上限挡掉"这个状态——装不下是模型的活，不是引擎的。

失败语义（必须写死，否则实现时一定被写成"静默忽略"）：

| 哪一步失败 | 行为 |
|---|---|
| `description` / `title` 解析不出 | 折叠失败——没有日志的折叠等于没折 |
| 新白板超过 1500 token | **拒收新板**，白板不变，记一条错误事件（不是静默截断：截断会悄悄吃掉一条约束） |
| 新白板为空但旧板非空 | 拒收。清空白板必须显式——否则一次解析失误就抹掉全部现状 |

### 3.8 两种文本的固定节

**`description`（本折日志）—— 三段过去时 + 两个附节，约 400 token**

| 节 | 写什么 | 谁写 |
|---|---|---|
| `## 意图` | 折叠那一刻打算做什么（折叠前的白板全文） | **机械抄**（`folds.intent`） |
| `## 行动` | 实际做了什么、结果如何（验证结论写在这里，**不单开一节**） | 模型 |
| `## 遗留` | 没做成什么、为什么、留给下一折 | 模型 |
| `## 提交` | 这一折的 commit（短 sha + 标题） | **机械抓**；抓不到就留空 |
| `## 关键词` | 检索原文用的词（文件 / 工具 / 报错 / 未结事项） | 模型 |

- **没有 `## 阶段` / `## 验证`**：两节都是"这一折做了什么"，分开写就是同一件事说两遍，而且模型会
  写成两套不一致的描述。验证结论属于行动的结果。
- **没有 `## 改动`（文件清单）**：文件清单能从 commit 里查，Git 才是权威。描述里只需要一串 commit
  当索引。
- **没有 `## 目标` / `## 下一步` / `## 约束` / `## 教训`**：它们回答"现在是什么"，住白板。
  `## 意图` 回答的是"**当时**打算干什么"，是历史事实，不是白板副本（白板会变，它不变）。
- **`## 提交` 必须机械填**：sha 不许由模型写——写错一个字符就是一个指向不存在对象的指针，而账本上
  看不出来。抓不到就留空（无事实不写键）。

**白板 —— `runs.board`，一整块文本，预算 1500 token（≈ 1000 汉字）**

它是**一列文本**，不是条目表。理由：渲染时整块拼进上下文，没有按条目查询的读者；
条目化（分类、条目上限、淘汰规则）是**模型在文本内部自己维持的东西**，引擎不解析。

引擎只做三件机械的事：

| 做什么 | 判据 |
|---|---|
| 长度校验 | ≤1500 token，超了拒收（§3.7） |
| 整块替换 | 不合并、不追加 |
| 留审计 | 折叠前的那一版进 `folds.intent`（机械抄），于是每一折的"改写前"都在账本上 |

推荐结构（prompt 约定，不是 schema）：

```
## 约束     （用户定的、违反就出错）
## 待办     （doing / waiting）
## 教训     （踩过的坑）
## 事实     （关键路径、常量、环境）
## 当前阶段 （一行）
```

**准入判据**：不记住的后果必须是一次**可观测的失败**（重复劳动 / 违反约束 / 重跑已失败的路）。
写不出这个后果的条目，说明它只是"看起来重要"。

**退场靠状态，不靠时间**：条目被撤销 / 被推翻 / 被证伪时才删。没有"多久没用到就忘掉"这条规则——
遗忘已经天然存在（保留区滑过去就模糊），白板是**对抗**遗忘的地方，不是加速它的地方。

### 3.9 折叠前的闸门

增量日志 + 白板漏记 = 那条信息永久离开上下文，而账本上看不出异常（折叠本身没错）。所以需要一道闸门，
但**只取机械可判的那一半**：

> 本折切点之前存在**没有 `tool_result` 的 `tool_use`** ⇒ 拒绝折。

"白板有没有对应条目"**不做闸**（无法机械判定）——改为折叠 prompt 强制产出"本折遗留事项"清单，
写进 `description` 的 `## 遗留`。

### 3.10 不做"摘要的摘要"

分层的目的只是"保留可追溯的骨架"，而骨架用**分组行 + 指针**表达：200 token，零调用，不失真。
再叠一层摘要要一次 LLM 调用 + 一份独立预算 + 自己也会膨胀，且每层都改写一遍，越往上越不准。

**层数上限 2（白板 + 日志）**。想加第三层，先回答"这一层的信息能不能压成 200 token 的阶段线"。
能，就不加层；不能，说明要的是"回忆细节"，那是账本的活，不是上下文的活。

## 4. 形状的不变量

这十二条是"形状对不对"的判据，不是测试用例：

1. **原文不复制**：被折走的正文只在 `messages` 里存一份。
2. **旧日志不重写**：每次折叠只追加一行，历史行永不被改写。
3. **渲染确定性**：同一批 `folds` + 同一预算 ⇒ 逐字节相同的输出。
4. **降级不夹断**：任何一条要么整条进，要么降一档。
5. **永远不出现"零历史"**：至少一条分组行。
6. **机械填的节不许模型写**：`## 意图` 逐字等于 `intent` 的渲染结果；`## 提交` 的 sha 来自工具结果。
7. **每一折可单独编码**：拎出 `title` + `description` + `(run_id, seq)` 就够，不依赖同一会话的其它行。
8. **停要说清**：终局必须写 `termination_reason`（+ `termination_detail`），不许静默降级；验证跑没跑、为什么没跑写 `verification_status` / `verification_reason`。（预算/实测/超出多少这几个数今天**不存在**，它们是落地要求，不是形状已承诺的字段。）
9. **一条信息只住一处**：现状→白板，历史→日志，细节→账本，常量→项目指令；**机械内容各自成列**，不混进 `description`。
10. **轮行与消息同一事务落盘**：不存在「半行」。崩溃的形状是「这一轮没有行」，而「轮跑到一半」的证据在消息层——
    **悬空的 `tool_use`**（没有对应 `tool_result`），§3.9 的闸门判它。
11. **顺序靠自然键**：轮内 `msg_seq`，跨轮 `round_no`，折叠 `folds.seq`。没有全局序号，`ts` 不作顺序依据。
12. **恢复不猜状态**：未结清的工具调用，恢复时不自动重跑，只补一条"状态未知"的桩，判断交给模型。

## 5. 为什么是这个形状

对比"一份累计文档"（今天的形状）：

| | 一份累计文档 | 本形状 |
|---|---|---|
| 每次折叠 | 重写整份，旧内容被二次压缩 | **只追加一条**，旧的一个字不动 |
| 摘要长度 | 随折数增长（实测 3.9k → 5.9k → 6.9k token） | 固定预算内可塑 |
| 失真 | 每折一次，越往上越不准 | 局部日志只压一次 |
| 降级 | 隐式（夹断） | **显式**（title / 分组行） |
| 可审计 | "哪条被挤掉了"无解 | 每条都在账本里，只是渲染得粗 |
| 成本 | 随折数增长 | 恒定 |

实测依据：一份 2,019 轮的会话，折叠 3 次，摘要 3.9k → 5.9k → 6.9k token，占折叠前上下文 1.2%–1.6%。
按本形状，同样 3 次折叠是 3 × 400 ≈ 1.2k，不随折数增长。

另一个数：按本形状的预算（200k 窗口、历史层 5k），**10 次折叠（约 6000 轮）全部能按完整
description 放下**——梯度降级在这个规模上用不到，它是给 10 万轮准备的。

## 6. 刻意不做

- **不做遗忘曲线 / 时间衰减**：遗忘已经天然存在——召回的信息留在保留区就清晰，保留区滑过去就模糊。
  该设计的是"什么不该被遗忘"（白板），不是"多久该忘"。
- **不做摘要的摘要**：只做梯度渲染（§3.10）。
- **不建 segment 表**：`rounds`（会话累计轮号）与 `runRounds`（本次拉起消耗）两个计数器确实不同，
  但没有读者需要那个边界；要归因成本就查 `llm_call` 按轮聚合，不为此多一张表。
- **不把白板做成 `notes` 的一个维度**：实测 142 个会话——89% 从不折叠；`note_list`（目录）全库
  只调了 4 次；`pinned` 写过 10 次，全是 e2e/测试噪声，一次都没改变过任何决定；折叠后读笔记
  真实发生 **1 次**。一个“每轮都要在眼前”的东西，需要的是一列文本，不是表里多一个标记。
- **不引入 ORM / SQL 依赖**：DB 只是宿主的一种实现，`src/` 里仍只有 JSONL 与内存两种。
  Node 22+ 内置 `node:sqlite`，"CLI 自建 SQLite"在零依赖红线内可行——但那是**宿主的可选实现**，
  不是形状的一部分。
- **不要求存储提供自增 / 序列**：序号由写入方（引擎）分配、账本只播种（§1.3）。形状只要求
  "能按自然键排序"。
- **不把 `content` 拆到块一级**：原子单位是**消息**。
- **不记录"工具执行过"的证据**：引擎能确定的只有两种——有 `tool_result`（跑过）/ 没有（**不知道**）。
  "不知道"如实告诉模型（补一条状态未知的桩），由它去查实际状态再决定要不要重来。
  为省一轮而记一行证据，等于为少见事件付每次工具调用的成本；而且猜错的方向都是坏的
  （猜"没跑"⇒重跑⇒副作用重复；猜"跑过"⇒撒谎⇒模型以为文件写好了）。
- **不做"无限保留历史原文"**：原文在账本里，上下文只放骨架。
- **不给白板加时间维度**：退场靠状态（done / 被推翻 / 被证伪），不靠"多久没用到"。
- **不在 `folds` 里存向量**：会话内它永远不会触发——200k 窗口下 10 折（约 6000 轮）全部能按完整
  description 放下；而跨库语义检索的索引是**宿主的职责**（键是项目/用户/折，引擎手里只有一 run 一个文件）。
  引擎侧也不能实现 embedding（零依赖）。形状对索引的唯一承诺是：**每一折都能被单独编码**（§3.4 ③）。

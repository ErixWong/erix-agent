## 0. 目标与边界

折叠只有一个目的：**在预算内，让模型仍然能做对下一步决定。**

不是"保存历史"（账本负责），不是"压缩率"（那是手段）。

由此得到唯一的分拣判据：

| 信息 | 去哪 |
|---|---|
| 模型下一步需要、而它**自己拿不到**的 | 进上下文（白板 / 折叠日志） |
| 模型**能自取**的（文件内容、历史细节、命令输出） | 留在账本，按需查 |
| **不变的**（项目规矩、常量、常识） | 项目指令，不进折叠 |
| **会变的现状**（待办、约束、教训） | 白板，覆盖写 |
| **这一段发生了什么** | 折叠日志，只追加 |

时间维度的划分是这套形状的骨架：**白板是现在时，折叠日志是过去时，项目指令是无时态，账本是全部时态。**

## 1. 表

### 1.1 `runs` —— 会话

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK** | 跨 resume 不变 |
| `status` | text | | 终态字符串 |
| `state` | jsonb | | run-state 载荷（预算 / 工具统计 / 折叠计数 / 终止原因） |
| `state_schema_version` | int | not null | 格式代次 |
| `state_epoch` | int | not null | **「状态块注入过几次」的计数**，用来判派生缓存（`semantic` 小抄目录）是否过期。不是版本号：只在注入轮 +1，失败收尾那次会用同一个号重写 |
| `created_at` / `updated_at` | timestamptz | not null | |

`state_epoch` 这个名字是有意的：`stateVersion` 会被所有人读成"版本号"，而它数的只是注入次数。

### 1.2 `rounds` —— 行流（**不存折叠事实**）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK₁**, FK→runs | |
| `seq` | bigint | **PK₂** | run 内严格递增（落盘序） |
| `round` | int | not null | 轮号 ≥ 0；`0` 是 seed 行 |
| `kind` | text | not null | `round` / `message` / `control` / `fact` |
| `dedup_key` | text | not null | 写侧幂等身份 |
| `payload_fingerprint` | text | not null | 规范化 JSON 的摘要，形状 `sha256:<24 hex>` |
| `payload` | jsonb | not null | 行内容（`kind='message'` 时是一条消息，content 块留在 payload 里） |
| `created_at` | timestamptz | not null | |

`payload` 不拆到块一级：原子单位是**消息**。只有需要 `tool_use ↔ tool_result ↔ 执行证据` 三向 join 时才拆。

**幂等的三态**（唯一约束表达不了）：同 key 同指纹 ⇒ 幂等 no-op；同 key **异**指纹 ⇒ 冲突，
既不覆盖也不静默丢；新 key ⇒ 插入。单纯 `ON CONFLICT DO NOTHING` 会把第二种吞掉。

### 1.3 `folds` —— 一次折叠 = 一行

**折叠的产物不是一份累计文档，而是一条局部日志。** 旧行一个字都不改。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` / `seq` | text / bigint | **PK(run_id, seq)** | `seq` = run 内严格递增折叠序 |
| `from_round` / `to_round` | int | not null | 本折吃掉的轮区间 |
| `prior_seq` | bigint | FK→folds(run_id, seq)，可空 | 续写基底 = 上一折。**用外键，不用哈希** |
| `title` | text | not null | **模型写的短标题**，≤ 60 字符 |
| `title_src` | text | not null | `model` / `first_line`（回退，见 §3.4 ①） |
| `description` | text | not null | **本折日志正文**（§3.8 的三段过去时） |
| `description_tokens` | int | not null | 渲染时按它算预算 |
| `intent` | jsonb | not null | **折叠前白板的待办快照**（机械抄，不是模型写的） |
| `stage_no` | int | 可空，FK→stages | 归属的阶段线（§3.2 第三档） |
| `source` | text | not null | `llm` / `host`（**没有 `statistical`**） |
| `origin` | text | not null | `semantic` / `host`（**没有 `mechanical`**） |
| `trigger` | text | not null | `budget` / `context_window_recovery` / `manual` |
| `superseded_by` | bigint | 可空，FK→folds(run_id, seq) | 被后来的某一折取代。**只加指针，不改行** |
| `created_at` | timestamptz | not null | |

**折叠的身份是三元组** `(from_round, to_round, prior_seq)`：同一区间先后两次折（恢复前 `prior_seq=NULL`、
恢复后 `prior_seq=3`）是**两次折叠**，不是一次。哈希身份是为"没有行 id 的存储"发明的，有了主键就没有理由。

**没有 `text`（累计体）**：累计体每折被重写一次，同一段内容会被压缩两遍、三遍（§5 有实测）。

### 1.4 `fold_round_rows` —— 这一折吃掉了哪些行

`(run_id, round)` **不唯一**（崩溃轮有消息行 + 轮载体行；同一轮在 restore / 重折之后可能有多代行），
所以「用轮号区间反查原文」**定位不到那一代行**。必须记成员关系：

| 列 | 约束 |
|---|---|
| `fold_run_id`, `fold_seq` | FK → `folds(run_id, seq)`，**PK₁₂** |
| `round_run_id`, `round_seq` | FK → `rounds(run_id, seq)`，**PK₃₄** |
| `excluded` | bool not null default false + `exclude_reason`（`clamped` / `deduped` / `safety_removed`） |

**原文一条都不复制。** 「被折走的原文」是派生查询：

```sql
SELECT r.* FROM fold_round_rows m JOIN rounds r ON r.run_id = m.round_run_id AND r.seq = m.round_seq
 WHERE m.fold_run_id = ? AND m.fold_seq = ? AND m.excluded = false;
```

实测依据：一份真机归档里，被归档的副本 940,278 字节，而它拷贝的那些行自己合计 941,379 字节
——**差 0.1%，等于纯冗余**。

### 1.5 `stages` —— 阶段线

折数一多，`title` 也是线性增长的（1000 折 × 20 token = 20k）。最老的那些按区间并成一行。

| 列 | 类型 | 约束 |
|---|---|---|
| `run_id` | text | **PK₁** |
| `stage_no` | int | **PK₂** |
| `from_fold_seq` / `to_fold_seq` | bigint | not null，闭区间 |
| `label` | text | not null，≤ 40 字符；`label_src` 记 `model` / `mechanical` |

分组是机械的（按区间），阶段名让 LLM 每 10 折起一次——**很便宜，不需要"摘要的摘要"**。
已并进 stage 的折不再出现在第一、二层（§3.2 的 ③ 独占它们）。

### 1.6 `notes` / `note_history` / `note_ops` —— 白板是 note 的一个维度

| 列 | 类型 | 说明 |
|---|---|---|
| `notes(run_id, key)` | PK | `current jsonb` / `state` / `pinned` / `relevance` / `provenance` / `created_at` / `updated_at` |
| `notes.board` | text，可空 | `NULL` = 长尾笔记（可检索、会过期）；`'whiteboard'` = 白板（强制注入、不过期、有预算） |
| `note_history(run_id, key, version)` | PK | 历史版本（ADR-018） |
| `note_ops(run_id, log_seq)` | PK | 操作记录：`key` / `board` / `op`（`write` / `complete` / `revoke` / `purge` / `drop`）/ `fold_seq` / `before` / `after` / `ts` |

**白板不新造实体**：白板和笔记的差别不在"是什么"，在三个策略——是否强制注入、有没有预算、会不会过期。
这三个都是属性，不是结构。

**准入判据**：不记住的后果必须是一次**可观测的失败**（重复劳动 / 违反约束 / 重跑已失败的路）。
写不出这个后果的条目，说明它只是"看起来重要"。

### 1.7 `budget_verdict` —— 装不下的证据

「超预算就显式失败」只有在**说清差多少**时才成立。

| 列 | 类型 | 说明 |
|---|---|---|
| `run_id` / `round` / `check_idx` | text / int / int | **PK** |
| `source` | text | `estimate`（引擎本地数）/ `provider`（真实 tokenizer 报超窗） |
| `fold_seq` | bigint | 哪一折之后数的，可空 |
| `budget_tokens` / `measured_tokens` | bigint | not null |
| `over_by` | bigint | 生成列：`greatest(measured - budget, 0)` |
| `layers_tried` | jsonb | 按尝试顺序：`["ttl","aggregate","stub"]` |
| `outcome` | text | `ok` / `degraded` / `failed` |
| `ts` | timestamptz | |

### 1.8 `recovery_rows` —— 恢复行（两族语义不同）

| 列 | 类型 | 说明 |
|---|---|---|
| `run_id` / `seq` | text / bigint | **PK** |
| `event` | text | `tool-executed` / `tool-result-unledgered` / `partial-text` |
| `round` | int | 槽事件按轮定界 |
| `dedup_key` / `payload_fingerprint` / `payload` / `created_at` | | 同 §1.2 的冲突判定 |

- `event = 'partial-text'`：**槽**——同 `(run_id, round)` 只留一条、原子替换、跨轮自剪枝；
- 其余事件：**只追加、永不替换、一行不丢**。

### 1.9 关系总图

```
runs 1─┬─N rounds ──────────┐
       ├─N folds ───────────┤ fold_round_rows (folds N─N rounds，精确到行)
       │      └─N:1 stages  │
       ├─N recovery_rows    │
       ├─N budget_verdict   │
       └─N notes 1─N note_history
                └─N note_ops
```

## 2. 事实归属：什么东西住哪里

同一个名字在账本里可能有四个不同的东西，混起来就会"恢复两遍"或"挤掉真相"：

| 东西 | 真实身份 | 归属 |
|---|---|---|
| `folds.title` / `folds.description` / `folds.intent` | **折叠事实**（本折日志） | `folds` |
| 实际喂给模型的那串字节 | **请求事实**。今天字段名有两个，别混：`foldedSummary.text` 是折叠后**整条消息**的投影（含原任务正文与安全层插的 `[已修剪]`）；`foldedSummary.fedSummaryText` 才是「写侧当场证得的那一块」逐字副本 | 留在**该轮的记录**上，不从 `folds` 派生 |
| `requestStateBlock` | run 状态块的渲染 | run-state |
| `foldedPayload` | 被折走的原始消息 | **派生**（§1.4 的行集合查询），不落正文 |
| `compactionStats[].foldSummary` | 指标 | 诊断面，只放信号 |

**写点后移**：喂给模型的那串字节要在**请求组装处**（所有压缩层定稿之后）写。于是它记的就是"模型真正
看到的那一串"，不再需要「钉住块对象身份 + 自证」。

## 3. 上下文组装

### 3.1 四层

```
┌────────────────────────────────────────────┐
│ 系统提示        固定（项目指令、常量、规矩）    │
├────────────────────────────────────────────┤
│ 遥远的回忆      只留 title，按轮次升序          │
├────────────────────────────────────────────┤
│ 详细日志        title + description，按轮次升序 │
├────────────────────────────────────────────┤
│ 白板            现状（约束 / 待办 / 教训 / 事实）│
├────────────────────────────────────────────┤
│ 活跃保留区      最近 K token 的原始消息          │
└────────────────────────────────────────────┘
```

**关键性质：不重写。** 每次折叠只追加一条 `folds` 行；旧行一个字不动。所谓"渐变"是
**对同一批日志按预算做梯度渲染**，不是"再摘要一次"。

### 3.2 渲染算法（确定性，零 LLM）

```
B = 窗口 × 2.5%                       ← 历史层预算（白板另算）
从最新一折往回：
  ① 60% B 给 description（每条 ≤ 500 token）
  ② 30% B 给 title（每条 ≤ 20 token）
  ③ 剩下给阶段线（每 10 折一行）
```

同一批记录 + 同一个预算 ⇒ 同一输出。

### 3.3 预算

| 用途 | 200k 窗口 | 512k 窗口 |
|---|---|---|
| 白板（固定 **1500 token ≈ 1000 汉字**，不随窗口缩放） | 1.5k | 1.5k |
| 详细日志（60% B） | 3.0k | 7.7k |
| 遥远的回忆（30% B） | 1.5k | 3.8k |
| 阶段线（10% B） | 0.5k | 1.3k |
| **历史层合计（B = 2.5%）** | **5.0k** | **12.8k** |
| **白板 + 历史层** | **6.5k（3.3%）** | **14.3k（2.8%）** |
| 活跃保留区（4%） | 8k | 20k |
| 余量 | 16k | 16k |

白板**不跟着窗口缩放**：它的大小由"必须一直在的东西有多少"决定。窗口小的时候宁可少放几条日志，
不少放一条约束。

### 3.4 三条硬前提（缺一条这套就塌）

1. **`title` 必须是模型写的短标题。** 回退到"正文首行"的记录做不了"遥远的回忆"——它不是标题。
   回退必须留 `title_src='first_line'`，且这种记录**不进第一层**。
2. **`description` 必须自解释。** 每条会被单独拿出来按轮次排列，脱离上下文读。出现"上面 / 刚才 /
   该文件 / 前面提到"这类指代即不合规。
3. **必须有阶段线。** 否则 `title` 数量线性增长（§1.5）。

### 3.5 渲染的边界与退化

| 情况 | 行为 |
|---|---|
| 估算与真实 tokenizer 不一致 | 按 **0.9B** 渲染；provider 报超窗 ⇒ 记一行 `budget_verdict`、**降一档重试一次** |
| 窗口极小（装不下一条 description + 一条 title） | 降级顺序：最新一条 description → 只给 title → 只给阶段线 |
| 连一条阶段线都装不下 | **`cannot_fit` 显式失败**。不许静默只给保留区——模型会以为自己是从头开始的 |
| 任何一档装不下整条 | **降档，不夹断**。半条 description 比没有更坏：模型会补全不存在的细节 |

**永远不出现"零历史"**：至少留一条阶段线，让模型知道"你看到的历史是被折过的"。

### 3.6 白板与日志的分界

| 说的是 | 住哪 |
|---|---|
| "现在是什么"（约束、待办、已知的坑、当前阶段） | 白板 |
| "这一折发生了什么"（做了什么、结果如何、为什么这么改） | 日志 |

两处都写的后果不是浪费 token，是模型读到**两份略有出入的版本**，然后按其中一份行动。

这条边界靠 prompt 约束 + 人工评审守，**不做脚本闸**——措辞类判定写 `if/else` 只会把注意力换成改常量。

### 3.7 折叠时一次调用产出三件事

1. `description`（本折日志）
2. `title`（短标题）
3. **白板更新指令**（`add` / `update` / `drop` 的结构化清单）

分开调用是两次付费、两次延迟，而且第二次看不到第一次的输入。

失败语义（必须写死，否则实现时一定被写成"静默忽略"）：

| 哪一步失败 | 行为 |
|---|---|
| `description` / `title` 解析不出 | 折叠失败——没有日志的折叠等于没折 |
| 白板更新指令解析不出 | **折叠照常落账**，白板不变，记一条错误事件。**不许**写空的 `note_ops`（没发生操作就不留操作记录） |
| 某条 `add` 超过白板上限 | 该条不进，记一条 `op='drop'` 说明是被上限挡的（不是模型没提） |

### 3.8 两种文本的固定节

**`description`（本折日志）—— 三段过去时 + 两个附节，约 400 token**

| 节 | 写什么 | 谁写 |
|---|---|---|
| `## 意图` | 折叠那一刻打算做什么（折叠前白板的 doing / waiting 条目） | **机械抄**（`folds.intent`） |
| `## 行动` | 实际做了什么、结果如何（验证结论写在这里，**不单开一节**） | 模型 |
| `## 遗留` | 没做成什么、为什么、留给下一折 | 模型 |
| `## 提交` | 这一折的 commit（短 sha + 标题） | **机械抓**；抓不到就留空 |
| `## 关键词` | 检索原文用的词（文件 / 工具 / 报错 / 未结事项） | 模型 |

- **没有 `## 阶段` / `## 验证`**：两节都是"这一折做了什么"，分开写就是同一件事说两遍，而且模型会
  写成两套不一致的描述。验证结论属于行动的结果。
- **没有 `## 改动`（文件清单）**：文件清单能从 commit 里查，Git 才是权威。描述里只需要一串 commit
  当索引。
- **没有 `## 目标` / `## 下一步` / `## 约束` / `## 教训`**：它们回答"现在是什么"，住白板。
  `## 意图` 回答的是"**当时**打算干什么"，是历史事实，不是白板副本（白板会变，它不变）。
- **`## 提交` 必须机械填**：sha 不许由模型写——写错一个字符就是一个指向不存在对象的指针，而账本上
  看不出来。抓不到就留空（无事实不写键）。

**白板 —— 预算 1500 token（≈ 1000 汉字），4 类条目 + 1 条阶段线**

| 类（`kind`） | 渲染成 | 条目上限 | 单条上限 | 退场条件 |
|---|---|---|---|---|
| `constraint` | `## 约束` | 5 | 55 字 | 用户撤销 / 任务结束 |
| `todo` | `## 待办`（doing / waiting） | 6 | 45 字 | done（保留行但不注入） |
| `lesson` | `## 教训` | 2 | 70 字 | 被推翻 / 不再相关 |
| `fact` | `## 事实`（关键路径、常量、环境） | 4 | 45 字 | 被证伪 |
| 阶段线 | `## 阶段线` 一行 | 1 | 40 字 | 不淘汰 |

合计：5×55 + 6×45 + 2×70 + 4×45 + 40 + 段头 40 ≈ **945 字 ≈ 1400 token**，卡在 1500 以内。

白板**不是散文，是条目清单**：渲染时按上表顺序拼成 5 段，每段内按 `pinned` → `relevance` →
`updated_at` 排。退场条件是**状态**（done / 被推翻 / 被证伪），不是"多久没用到"。

### 3.9 折叠前的闸门

增量日志 + 白板漏记 = 那条信息永久离开上下文，而账本上看不出异常（折叠本身没错）。所以需要一道闸门，
但**只取机械可判的那一半**：

> 区间内存在**没有 `tool_result` 的 `tool_use`** ⇒ 拒绝折。

"白板有没有对应条目"**不做闸**（无法机械判定）——改为折叠 prompt 强制产出"本折遗留事项"清单，
与白板的差异记进 `note_ops`，供人复核。

### 3.10 不做"摘要的摘要"

分层的目的只是"保留可追溯的骨架"，而骨架用**阶段线 + 指针**表达：200 token，零调用，不失真。
再叠一层摘要要一次 LLM 调用 + 一份独立预算 + 自己也会膨胀，且每层都改写一遍，越往上越不准。

**层数上限 2（白板 + 日志）**。想加第三层，先回答"这一层的信息能不能压成 200 token 的阶段线"。
能，就不加层；不能，说明要的是"回忆细节"，那是账本的活，不是上下文的活。

---

## 4. 形状的不变量

这八条是"形状对不对"的判据，不是测试用例：

1. **原文不复制**：被折走的正文只在 `rounds` 里存一份。
2. **旧日志不重写**：每次折叠只追加一行，历史行永不被改写。
3. **渲染确定性**：同一批 `folds` + 同一预算 ⇒ 逐字节相同的输出。
4. **降级不夹断**：任何一条要么整条进，要么降一档。
5. **永远不出现"零历史"**：至少一条阶段线。
6. **机械填的节不许模型写**：`## 意图` 逐字等于 `intent` 的渲染结果；`## 提交` 的 sha 来自工具结果。
7. **装不下要说清**：失败时 `budget_verdict` 给出 budget / measured / over_by / layers_tried。
8. **一条信息只住一处**：现状→白板，历史→日志，细节→账本，常量→项目指令。

## 5. 为什么是这个形状

对比"一份累计文档"（今天的形状）：

| | 一份累计文档 | 本形状 |
|---|---|---|
| 每次折叠 | 重写整份，旧内容被二次压缩 | **只追加一条**，旧的一个字不动 |
| 摘要长度 | 随折数增长（实测 3.9k → 5.9k → 6.9k token） | 固定预算内可塑 |
| 失真 | 每折一次，越往上越不准 | 局部日志只压一次 |
| 降级 | 隐式（夹断） | **显式**（title / 阶段线） |
| 可审计 | "哪条被挤掉了"无解 | 每条都在账本里，只是渲染得粗 |
| 成本 | 随折数增长 | 恒定 |

实测依据：一份 2,019 轮的会话，折叠 3 次，摘要 3.9k → 5.9k → 6.9k token，占折叠前上下文 1.2%–1.6%。
按本形状，同样 3 次折叠是 3 × 400 ≈ 1.2k，不随折数增长。

另一个数：按本形状的预算（200k 窗口、历史层 5k），**10 次折叠（约 6000 轮）全部能按完整
description 放下**——梯度降级在这个规模上用不到，它是给 10 万轮准备的。

## 6. 刻意不做

- **不做遗忘曲线 / 时间衰减**：遗忘已经天然存在——召回的信息留在保留区就清晰，保留区滑过去就模糊。
  该设计的是"什么不该被遗忘"（白板），不是"多久该忘"。
- **不做摘要的摘要**：只做梯度渲染（§3.10）。
- **不建 segment 表**：`rounds`（会话累计轮号）与 `runRounds`（本次拉起消耗）两个计数器确实不同，
  但没有读者需要那个边界；要归因成本就查 `llm_call` 按轮聚合，不为此多一张表。
- **不引入 ORM / SQL 依赖**：DB 只是宿主的一种实现，`src/` 里仍只有 JSONL 与内存两种。
- **不把 `payload` 拆到块一级**：原子单位是**消息**。
- **不做"无限保留历史原文"**：原文在账本里，上下文只放骨架。
- **不给白板加时间维度**：退场靠状态（done / 被推翻 / 被证伪），不靠"多久没用到"。

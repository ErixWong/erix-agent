## 0. 目标与边界

折叠只有一个目的：**在预算内，让模型仍然能做对下一步决定。**

不是"保存历史"（账本负责），不是"压缩率"（那是手段）。

由此得到唯一的分拣判据：

| 信息 | 去哪 |
|---|---|
| 模型下一步需要、而它**自己拿不到**的 | 进上下文（白板 / 折叠日志） |
| 模型**能自取**的（文件内容、历史细节、命令输出） | 留在账本，按需查 |
| **不变的**（项目规矩、常量、常识） | 项目指令，不进折叠 |
| **会变的现状**（待办、约束、教训） | 白板，覆盖写 |
| **这一段发生了什么** | 折叠日志，只追加 |

时间维度的划分是这套形状的骨架：**白板是现在时，折叠日志是过去时，项目指令是无时态，账本是全部时态。**

## 1. 表

### 1.1 `runs` —— 会话（session）

> **`runs` 就是 session。** 表名与列名保留 `runs` / `run_id`，是因为公开面（契约、事件、宿主代码）
> 早已这么叫；**语义上它就是会话**，本文正文一律写"会话"。

**一行 = 一个 `runId` = 一个会话（session）。** CLI 的 `--session <id>` 就是它
（`runId = options.session ?? 默认 id`），resume / `-c` 续的是同一个 id，所以也是同一个文件、同一行。

⚠ **`run` 这个词在代码里被用成两个意思**，别混：

| 说 "run" 时指 | 是不是一行 |
|---|---|
| 会话（`runId`） | **是**，就是本表一行 |
| 一次 `runToolLoop` 调用 | **不是**。它只是往这个会话里追加轮次；`runRounds`（本次调用消耗的轮数，resume 后从 0 重算）是它的派生计数，不是实体 |

第二条不建模：它没有独立的生命周期，也没有读者需要那个边界（成本归因查 `llm_call` 按轮聚合就够）。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK** | 跨 resume 不变 |
| `status` | text | | 终态字符串 |
| `state` | jsonb | | run-state 载荷（预算 / 工具统计 / 折叠计数 / 终止原因） |
| `state_schema_version` | int | not null | 格式代次 |
| `state_epoch` | int | not null | **「状态块注入过几次」的计数**，用来判派生缓存（`semantic` 小抄目录）是否过期。不是版本号：只在注入轮 +1，失败收尾那次会用同一个号重写 |
| `created_at` / `updated_at` | timestamptz | not null | |

`state_epoch` 这个名字是有意的：`stateVersion` 会被所有人读成"版本号"，而它数的只是注入次数。

### 1.2 `rounds` —— 一行一轮（元数据）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK₁**, FK→runs | |
| `round_no` | int | **PK₂** | ≥ 0；`0` 是 seed |
| `status` | text | not null | `open` / `closed` / `crashed` |
| `started_at` / `closed_at` | timestamptz | | |
| `stop_reason` | text | | |
| `text_preview` | text | | 本轮正文的预览 |
| `tool_use_count` | int | not null default 0 | 本轮发起几个工具 |
| `usage` | jsonb | | 本轮**累计**用量（截断续写时是多次之和） |
| `response_usage` | jsonb | | **最后一发**的用量（历史形状） |
| `summary` | text | | 本轮自身摘要 |
| `l0facts` / `wrapup` | jsonb | | |

**轮行先建后收口**：`open` → 消息落盘 → `closed`。这样消息的外键永远有主，而"崩溃在轮中"这个
形状由 `status='open'` 表达，不再靠"行缺失"。

### 1.3 `messages` —— 一行一条消息

消息是**最小单位**。每条消息属于且只属于一轮。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | text | **PK₁** | |
| `round_no` | int | **PK₂**, FK→rounds | 它属于哪一轮 |
| `msg_seq` | int | **PK₃** | 轮内单调，从 0 起 |
| `caller` | text | not null | **谁写的**：`user` / `assistant` / `tool` / `judge` / `engine` |
| `role` | text | not null | **协议要求它装成谁**：`user` / `assistant` / `system` |
| `part_of_msg_seq` | int | 可空，自引用 | **切片归属**：这条是某条逻辑消息的一个分片，指向**首片** |
| `content` | jsonb | not null | 块数组（`text` / `tool_use` / `tool_result` / `image`），保序 |
| `dedup_key` | text | not null | 写侧幂等身份 |
| `payload_fingerprint` | text | not null | 规范化 JSON 的摘要，形状 `sha256:<24 hex>` |
| `ts` | timestamptz | | 信封时刻（不是顺序依据） |

**`caller` 与 `role` 是两个维度，别合并**：

| `caller` | 是什么 | `role` |
|---|---|---|
| `user` | 人 / 宿主提问（`steer` 也走这里） | user |
| `assistant` | 模型返回（可同时带 text 和 tool_use） | assistant |
| **`tool`** | **工具结果** | **user** ← 协议把它塞进 user 消息，但作者不是用户 |
| `judge` | **judge 模型的评审意见**（引擎只是转述） | user |
| `engine` | 引擎自己的模板注入（“已到预算上限，请收尾” / guard revise） | user |

一致性约束：`caller='tool'` ⇔ 含 `tool_result` 块；`caller='assistant'` 可含 `tool_use` 块；
`caller='user'` 只含 text（提问）；`caller IN ('judge','engine')` 不含 `tool_result`。

**顺序从自然键推出来，不需要全局序号**：

| 要排什么 | 用什么 |
|---|---|
| 轮内消息 | `msg_seq` |
| 跨轮 | `round_no` |
| 折叠之间 | `folds.seq`（§1.4） |
| 恢复事件之间 | `recovery_rows.seq`（§1.9） |

全局 `seq` 是**单文件 JSONL 的产物**（一个文件里没有类型，只有行序）。拆成表之后，行序由自然键承担，
`ts` 只作记录、不作顺序依据（墙钟会回拨，同一毫秒还可能有多条）。

**序号由写入方分配，不是存储自增**——这条是形状级的，不是实现细节：

| | |
|---|---|
| 谁给号 | **引擎**（`nextMessageSeqByRound` 从已落盘行播种，轮内递增；折叠序同理） |
| 存储做什么 | 只持久化 + 提供播种用的读数 |
| 为什么不能用自增列 | 崩溃重跑必须拿到**同一个号**；存储自增每次都给新号，而"同一条消息换号"在账本上就是**同 key 异 payload = 冲突** |
| 代价 | 零：JSONL / 内存 / SQLite 三种存储一视同仁，不需要任何存储特性 |

顺带一条：Node 22+ 内置 `node:sqlite`（本机 v22 可用，带 ExperimentalWarning），所以"CLI 自建 SQLite"
在零依赖红线内是可行的。但它是**宿主的一种可选实现**，不是形状的一部分——形状只要求"能按自然键排序"。

**哪些消息进折叠**：`caller IN ('assistant','tool')`。`user` 不进——宿主的幂等判据要求
`load()` 能看见自己那条 `dedup_key`；`engine` 不进——它在轮记录落盘之后才产生。

**切片（`part_of_msg_seq`）—— 一行一条消息，但一条消息可以是多行**：

模型一次调 3 个工具，结果**每完成一个就落一行**（崩溃时不丢已完成的），靠 `part_of_msg_seq` 标
"我属于同一条逻辑消息"：

```
msg_seq=0  assistant  [text, tool_use(tu_1), tool_use(tu_2), tool_use(tu_3)]   ← 首片
msg_seq=1  tool       [tool_result(tu_1)]   part_of=null                        ← 首片
msg_seq=2  tool       [tool_result(tu_2)]   part_of=1
msg_seq=3  tool       [tool_result(tu_3)]   part_of=1
```

**折叠与渲染必须拼回一条**：协议要求一条 `tool_use` 由**紧随其后的那一条** user 消息结清；
拆成三条 user 消息发出去，provider 直接 400。

⚠ **`part_of` 只能指首片，不许链式指上一片**。链式会让"每隔一片落一次"（首片 → 指向它 →
指向分片），配对永久失败，而且坏形状是**静默的**：不报错、不丢块，只是工具结果再也配不上。

**“段”（人的一次提问 → 它引发的所有轮）是一条查询**：按 `caller='user'` 的消息切，不建表。

### 1.4 `folds` —— 一次折叠 = 一行

**折叠的产物不是一份累计文档，而是一条局部日志。** 旧行一个字都不改。

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` / `seq` | text / bigint | **PK(run_id, seq)** | `seq` = 会话内严格递增折叠序 |
| `from_round` / `to_round` | int | not null | 本折吃掉的轮区间 |
| `prior_seq` | bigint | FK→folds(run_id, seq)，可空 | 续写基底 = 上一折。**用外键，不用哈希** |
| `title` | text | not null | **模型写的短标题**，≤ 60 字符 |
| `title_src` | text | not null | `model` / `first_line`（回退，见 §3.4 ①） |
| `description` | text | not null | **模型写的三节**（行动 / 遗留 / 关键词），约 400 token |
| `description_tokens` | int | not null | 渲染时按它算预算 |
| `intent` | jsonb | not null | **折叠前白板的待办快照**（机械抄）——渲染成 `## 意图` |
| `commits` | jsonb | 可空 | 这一折的 commit（`[{sha, subject}]`，机械抓）——渲染成 `## 提交`；抓不到就空 |
| `source` | text | not null | `llm` / `host`（**没有 `statistical`**） |
| `trigger` | text | not null | `budget` / `context_window_recovery` / `manual` |
| `superseded_by` | bigint | 可空，FK→folds(run_id, seq) | 被后来的某一折取代。**只加指针，不改行** |
| `created_at` | timestamptz | not null | |

**折叠的身份是三元组** `(from_round, to_round, prior_seq)`：同一区间先后两次折（恢复前 `prior_seq=NULL`、
恢复后 `prior_seq=3`）是**两次折叠**，不是一次。哈希身份是为"没有行 id 的存储"发明的，有了主键就没有理由。

**没有 `stage_no`**：分组是渲染时现算的（§1.6），不在行上。

**没有 `text`（累计体）**：累计体每折被重写一次，同一段内容会被压缩两遍、三遍（§5 有实测）。

### 1.5 `fold_exclusions` —— 区间内的例外（**不记成员**）

第二版为"这一折吃掉了哪些行"专门记了一张成员表，理由是 `(run_id, round)` 不唯一——同一轮在
崩溃重跑 / restore / 重折之后可能有多代行。**拆成 `rounds` + `messages` 之后这个问题消失了**：
消息的主键是 `(run_id, round_no, msg_seq)`，一条消息只有一行，不存在"第几代"。

所以折叠的成员是**可推导的**：区间内的全部消息，减去例外。

| 列 | 约束 |
|---|---|
| `fold_run_id`, `fold_seq` | FK → `folds(run_id, seq)`，**PK₁₂** |
| `run_id`, `round_no`, `msg_seq` | FK → `messages`，**PK₃₄₅** |
| `reason` | `clamped` / `safety_removed`（`deduped` 随"不存副本"一起消失） |

**原文一条都不复制。** 「被折走的原文」是派生查询：

```sql
SELECT m.* FROM messages m
 WHERE m.run_id = ?
   AND m.round_no BETWEEN ? AND ?
   AND NOT EXISTS (SELECT 1 FROM fold_exclusions e
                    WHERE e.fold_seq = ? AND e.run_id = m.run_id
                      AND e.round_no = m.round_no AND e.msg_seq = m.msg_seq);
```

实测依据：一份真机归档里，被归档的副本 940,278 字节，而它拷贝的那些行自己合计 941,379 字节
——**差 0.1%，等于纯冗余**。

### 1.6 两样东西是渲染时算的，**不是表**

#### ① 分组行

折数一多，`title` 也是线性增长的（1000 折 × 20 token = 20k）。需要把最老的那些并成一行——
但这件事**不需要存储**：

> 按 `seq` 每 10 折一组，渲染时现算。组标签 = `第 a–b 折 · <组内第一折（跳过已作废的）的 title>`。

三点理由：

1. **它是纯函数**：`folds` 行只追加不改，所以每 10 折的边界永远不变，现算结果与存下来逐字相同。
2. **它不需要 LLM**：标签直接用组内第一折的 title（那本来就是模型写的）。存表就得另外调一次模型起名，
   多一份预算、多一条失败路径。
3. **它没有生命周期**：存表就要回答“新折进来要不要重分组”“旧组要不要作废”——现算不产生这种问题。

代价是标签质量略差（组内第一折的标题不一定概括整段）。可以接受：这一层是**回忆的指针**，
不是摘要——真要细节就去查账本。

#### ② 会话级概述

“这段会话到底干了什么”——宿主横幅与人类阅读都要它，但**也不要存**：

```sql
SELECT seq, title FROM folds
 WHERE run_id = ? AND superseded_by IS NULL ORDER BY seq;
```

拼出来就是概述；超过一定条数会自动并成分组行（①），再想细就拼 `description`。

**不存理由**：它是上面这些行的函数。一旦落进 `folds` 行（每折一份）就是 N 份越来越大的
累计快照——这正是被否掉的那个形状（实测摘要 3.9k → 5.9k → 6.9k token，涨的全是重复）。
即使只存“最新一份”，那也是一次**不可审计的重写**：模型每折压一遍，丢掉了什么账本上看不出来，
而它能提供的信息量，十条 title 已经给了。

### 1.7 `notes` / `note_history` / `note_ops` —— 白板是 note 的一个维度

| 列 | 类型 | 说明 |
|---|---|---|
| `notes(run_id, key)` | PK | `current jsonb` / `state` / `pinned` / `relevance` / `provenance` / `created_at` / `updated_at` |
| `notes.board` | text，可空 | `NULL` = 长尾笔记（可检索、会过期）；`'whiteboard'` = 白板（强制注入、不过期、有预算） |
| `note_history(run_id, key, version)` | PK | 历史版本（ADR-018） |
| `note_ops(run_id, log_seq)` | PK | 操作记录：`key` / `board` / `op`（`write` / `complete` / `revoke` / `purge` / `drop`）/ `fold_seq` / `before` / `after` / `ts` |

**白板不新造实体**：白板和笔记的差别不在"是什么"，在三个策略——是否强制注入、有没有预算、会不会过期。
这三个都是属性，不是结构。

**准入判据**：不记住的后果必须是一次**可观测的失败**（重复劳动 / 违反约束 / 重跑已失败的路）。
写不出这个后果的条目，说明它只是"看起来重要"。

### 1.8 `budget_verdict` —— 装不下的证据

「超预算就显式失败」只有在**说清差多少**时才成立。

| 列 | 类型 | 说明 |
|---|---|---|
| `run_id` / `round` / `check_idx` | text / int / int | **PK** |
| `source` | text | `estimate`（引擎本地数）/ `provider`（真实 tokenizer 报超窗） |
| `fold_seq` | bigint | 哪一折之后数的，可空 |
| `budget_tokens` / `measured_tokens` | bigint | not null |
| `over_by` | bigint | 生成列：`greatest(measured - budget, 0)` |
| `layers_tried` | jsonb | 按尝试顺序：`["ttl","aggregate","stub"]` |
| `outcome` | text | `ok` / `degraded` / `failed` |
| `ts` | timestamptz | |

### 1.9 `recovery_rows` —— 恢复行（两族语义不同）

| 列 | 类型 | 说明 |
|---|---|---|
| `run_id` / `seq` | text / bigint | **PK** |
| `event` | text | `tool-executed` / `tool-result-unledgered` / `partial-text` |
| `round` | int | 槽事件按轮定界 |
| `dedup_key` / `payload_fingerprint` / `payload` / `created_at` | | 同 §1.3 的冲突判定 |

- `event = 'partial-text'`：**槽**——同 `(run_id, round)` 只留一条、原子替换、跨轮自剪枝；
- 其余事件：**只追加、永不替换、一行不丢**。

### 1.10 关系总图

```
runs 1─┬─N rounds ──── N messages（消息是最小单位，每轮内按 msg_seq 排）
       ├─N folds ───────────┐
       │                    └─ fold_exclusions（区间内的例外，成员可推导）
       ├─N recovery_rows
       ├─N budget_verdict
       └─N notes 1─N note_history
                └─N note_ops
```

## 2. 事实归属：什么东西住哪里

同一个名字在账本里可能有四个不同的东西，混起来就会"恢复两遍"或"挤掉真相"：

| 东西 | 真实身份 | 归属 |
|---|---|---|
| `folds.title` / `folds.description` / `folds.intent` | **折叠事实**（本折日志） | `folds` |
| 实际喂给模型的那串字节 | **请求事实**。今天字段名有两个，别混：`foldedSummary.text` 是折叠后**整条消息**的投影（含原任务正文与安全层插的 `[已修剪]`）；`foldedSummary.fedSummaryText` 才是「写侧当场证得的那一块」逐字副本 | 留在**该轮的记录**上，不从 `folds` 派生 |
| `requestStateBlock` | 会话状态块的渲染 | run-state |
| **judge 决策**（done / confidence / reason / evidence / direction） | **控制流证据**，不进上下文、不参与渲染 | **外部账**：`judge.log`，按 `runId` join。形状只收它**注入的那条消息**（`caller='judge'`） |
| `foldedPayload` | 被折走的原始消息 | **派生**（§1.5 的区间 + 例外查询），不落正文 |
| `compactionStats[].foldSummary` | 指标 | 诊断面，只放信号 |

**写点后移**：喂给模型的那串字节要在**请求组装处**（所有压缩层定稿之后）写。于是它记的就是"模型真正
看到的那一串"，不再需要「钉住块对象身份 + 自证」。

## 3. 上下文组装

### 3.1 四层

```
┌────────────────────────────────────────────┐
│ 系统提示        固定（项目指令、常量、规矩）    │
├────────────────────────────────────────────┤
│ 遥远的回忆      只留 title，按轮次升序          │
├────────────────────────────────────────────┤
│ 详细日志        title + description，按轮次升序 │
├────────────────────────────────────────────┤
│ 白板            现状（约束 / 待办 / 教训 / 事实）│
├────────────────────────────────────────────┤
│ 活跃保留区      最近 K token 的原始消息          │
└────────────────────────────────────────────┘
```

**关键性质：不重写。** 每次折叠只追加一条 `folds` 行；旧行一个字不动。所谓"渐变"是
**对同一批日志按预算做梯度渲染**，不是"再摘要一次"。

### 3.2 渲染算法（确定性，零 LLM）

```
B = 窗口 × 2.5%                       ← 历史层预算（白板另算）
从最新一折往回：
  ① 60% B 给 description（每条 ≤ 500 token）
  ② 30% B 给 title（每条 ≤ 20 token）
  ③ 剩下给分组行（每 10 折一组，现算：`第 a–b 折 · <组内第一折的 title>`）
```

同一批记录 + 同一个预算 ⇒ 同一输出。**纯时间序，没有相关度排序**——原因见 §6。

### 3.3 预算

| 用途 | 200k 窗口 | 512k 窗口 |
|---|---|---|
| 白板（固定 **1500 token ≈ 1000 汉字**，不随窗口缩放） | 1.5k | 1.5k |
| 详细日志（60% B） | 3.0k | 7.7k |
| 遥远的回忆（30% B） | 1.5k | 3.8k |
| 分组行（10% B） | 0.5k | 1.3k |
| **历史层合计（B = 2.5%）** | **5.0k** | **12.8k** |
| **白板 + 历史层** | **6.5k（3.3%）** | **14.3k（2.8%）** |
| 活跃保留区（4%） | 8k | 20k |
| 余量 | 16k | 16k |

白板**不跟着窗口缩放**：它的大小由"必须一直在的东西有多少"决定。窗口小的时候宁可少放几条日志，
不少放一条约束。

### 3.4 四条硬前提（缺一条这套就塌）

1. **`title` 必须是模型写的短标题。** 回退到"正文首行"的记录做不了"遥远的回忆"——它不是标题。
   回退必须留 `title_src='first_line'`，且这种记录**不进第一层**。
2. **`description` 必须自解释。** 每条会被单独拿出来按轮次排列，脱离上下文读。出现"上面 / 刚才 /
   该文件 / 前面提到"这类指代即不合规。
3. **每一折必须能单独编码。** 这是形状对"跨库检索"的唯一承诺：`description` 拎出来（配 `title`
   与 `(run_id, seq)`）就足够让任何人算出一条可用的向量，不需要同一会话的其它行、不需要原任务。
   做不到这一条，检索层就永远得把整个会话塞进去才能判断相关度。
4. **必须有分组行。** 否则 `title` 数量线性增长（§1.6）。

### 3.5 渲染的边界与退化

| 情况 | 行为 |
|---|---|
| 估算与真实 tokenizer 不一致 | 按 **0.9B** 渲染；provider 报超窗 ⇒ 记一行 `budget_verdict`、**降一档重试一次** |
| 窗口极小（装不下一条 description + 一条 title） | 降级顺序：最新一条 description → 只给 title → 只给阶段线 |
| 连一条分组行都装不下 | **`cannot_fit` 显式失败**。不许静默只给保留区——模型会以为自己是从头开始的 |
| 任何一档装不下整条 | **降档，不夹断**。半条 description 比没有更坏：模型会补全不存在的细节 |

**永远不出现"零历史"**：至少留一条分组行，让模型知道"你看到的历史是被折过的"。

### 3.6 白板与日志的分界

| 说的是 | 住哪 |
|---|---|
| "现在是什么"（约束、待办、已知的坑、当前阶段） | 白板 |
| "这一折发生了什么"（做了什么、结果如何、为什么这么改） | 日志 |

两处都写的后果不是浪费 token，是模型读到**两份略有出入的版本**，然后按其中一份行动。

这条边界靠 prompt 约束 + 人工评审守，**不做脚本闸**——措辞类判定写 `if/else` 只会把注意力换成改常量。

### 3.7 折叠时一次调用产出三件事

1. `description`（本折日志）
2. `title`（短标题）
3. **白板更新指令**（`add` / `update` / `drop` 的结构化清单）

分开调用是两次付费、两次延迟，而且第二次看不到第一次的输入。

失败语义（必须写死，否则实现时一定被写成"静默忽略"）：

| 哪一步失败 | 行为 |
|---|---|
| `description` / `title` 解析不出 | 折叠失败——没有日志的折叠等于没折 |
| 白板更新指令解析不出 | **折叠照常落账**，白板不变，记一条错误事件。**不许**写空的 `note_ops`（没发生操作就不留操作记录） |
| 某条 `add` 超过白板上限 | 该条不进，记一条 `op='drop'` 说明是被上限挡的（不是模型没提） |

### 3.8 两种文本的固定节

**`description`（本折日志）—— 三段过去时 + 两个附节，约 400 token**

| 节 | 写什么 | 谁写 |
|---|---|---|
| `## 意图` | 折叠那一刻打算做什么（折叠前白板的 doing / waiting 条目） | **机械抄**（`folds.intent`） |
| `## 行动` | 实际做了什么、结果如何（验证结论写在这里，**不单开一节**） | 模型 |
| `## 遗留` | 没做成什么、为什么、留给下一折 | 模型 |
| `## 提交` | 这一折的 commit（短 sha + 标题） | **机械抓**；抓不到就留空 |
| `## 关键词` | 检索原文用的词（文件 / 工具 / 报错 / 未结事项） | 模型 |

- **没有 `## 阶段` / `## 验证`**：两节都是"这一折做了什么"，分开写就是同一件事说两遍，而且模型会
  写成两套不一致的描述。验证结论属于行动的结果。
- **没有 `## 改动`（文件清单）**：文件清单能从 commit 里查，Git 才是权威。描述里只需要一串 commit
  当索引。
- **没有 `## 目标` / `## 下一步` / `## 约束` / `## 教训`**：它们回答"现在是什么"，住白板。
  `## 意图` 回答的是"**当时**打算干什么"，是历史事实，不是白板副本（白板会变，它不变）。
- **`## 提交` 必须机械填**：sha 不许由模型写——写错一个字符就是一个指向不存在对象的指针，而账本上
  看不出来。抓不到就留空（无事实不写键）。

**白板 —— 预算 1500 token（≈ 1000 汉字），5 类条目**

| 类（`kind`） | 渲染成 | 条目上限 | 单条上限 | 退场条件 |
|---|---|---|---|---|
| `constraint` | `## 约束` | 5 | 55 字 | 用户撤销 / 任务结束 |
| `todo` | `## 待办`（doing / waiting） | 6 | 45 字 | done（保留行但不注入） |
| `lesson` | `## 教训` | 2 | 70 字 | 被推翻 / 不再相关 |
| `fact` | `## 事实`（关键路径、常量、环境） | 4 | 45 字 | 被证伪 |
| `phase` | `## 当前阶段` | 1 | 40 字 | 进入下一阶段时改写 |

合计：5×55 + 6×45 + 2×70 + 4×45 + 40 + 段头 40 ≈ **945 字 ≈ 1400 token**，卡在 1500 以内。

白板**不是散文，是条目清单**：渲染时按上表顺序拼成 5 段，每段内按 `pinned` → `relevance` →
`updated_at` 排。退场条件是**状态**（done / 被推翻 / 被证伪），不是"多久没用到"。

### 3.9 折叠前的闸门

增量日志 + 白板漏记 = 那条信息永久离开上下文，而账本上看不出异常（折叠本身没错）。所以需要一道闸门，
但**只取机械可判的那一半**：

> 区间内存在**没有 `tool_result` 的 `tool_use`** ⇒ 拒绝折。

"白板有没有对应条目"**不做闸**（无法机械判定）——改为折叠 prompt 强制产出"本折遗留事项"清单，
与白板的差异记进 `note_ops`，供人复核。

### 3.10 不做"摘要的摘要"

分层的目的只是"保留可追溯的骨架"，而骨架用**分组行 + 指针**表达：200 token，零调用，不失真。
再叠一层摘要要一次 LLM 调用 + 一份独立预算 + 自己也会膨胀，且每层都改写一遍，越往上越不准。

**层数上限 2（白板 + 日志）**。想加第三层，先回答"这一层的信息能不能压成 200 token 的阶段线"。
能，就不加层；不能，说明要的是"回忆细节"，那是账本的活，不是上下文的活。

## 4. 形状的不变量

这十一条是"形状对不对"的判据，不是测试用例：

1. **原文不复制**：被折走的正文只在 `messages` 里存一份。
2. **旧日志不重写**：每次折叠只追加一行，历史行永不被改写。
3. **渲染确定性**：同一批 `folds` + 同一预算 ⇒ 逐字节相同的输出。
4. **降级不夹断**：任何一条要么整条进，要么降一档。
5. **永远不出现"零历史"**：至少一条分组行。
6. **机械填的节不许模型写**：`## 意图` 逐字等于 `intent` 的渲染结果；`## 提交` 的 sha 来自工具结果。
7. **每一折可单独编码**：拎出 `title` + `description` + `(run_id, seq)` 就够，不依赖同一会话的其它行。
8. **装不下要说清**：失败时 `budget_verdict` 给出 budget / measured / over_by / layers_tried。
9. **一条信息只住一处**：现状→白板，历史→日志，细节→账本，常量→项目指令；**机械内容各自成列**，不混进 `description`。
10. **轮行先建后收口**：`open` → 消息落盘 → `closed`。消息的外键永远有主，崩溃形状是 `status='open'`，不是行缺失。
11. **顺序靠自然键**：轮内 `msg_seq`，跨轮 `round_no`，折叠 `folds.seq`。没有全局序号，`ts` 不作顺序依据。

## 5. 为什么是这个形状

对比"一份累计文档"（今天的形状）：

| | 一份累计文档 | 本形状 |
|---|---|---|
| 每次折叠 | 重写整份，旧内容被二次压缩 | **只追加一条**，旧的一个字不动 |
| 摘要长度 | 随折数增长（实测 3.9k → 5.9k → 6.9k token） | 固定预算内可塑 |
| 失真 | 每折一次，越往上越不准 | 局部日志只压一次 |
| 降级 | 隐式（夹断） | **显式**（title / 分组行） |
| 可审计 | "哪条被挤掉了"无解 | 每条都在账本里，只是渲染得粗 |
| 成本 | 随折数增长 | 恒定 |

实测依据：一份 2,019 轮的会话，折叠 3 次，摘要 3.9k → 5.9k → 6.9k token，占折叠前上下文 1.2%–1.6%。
按本形状，同样 3 次折叠是 3 × 400 ≈ 1.2k，不随折数增长。

另一个数：按本形状的预算（200k 窗口、历史层 5k），**10 次折叠（约 6000 轮）全部能按完整
description 放下**——梯度降级在这个规模上用不到，它是给 10 万轮准备的。

## 6. 刻意不做

- **不做遗忘曲线 / 时间衰减**：遗忘已经天然存在——召回的信息留在保留区就清晰，保留区滑过去就模糊。
  该设计的是"什么不该被遗忘"（白板），不是"多久该忘"。
- **不做摘要的摘要**：只做梯度渲染（§3.10）。
- **不建 segment 表**：`rounds`（会话累计轮号）与 `runRounds`（本次拉起消耗）两个计数器确实不同，
  但没有读者需要那个边界；要归因成本就查 `llm_call` 按轮聚合，不为此多一张表。
- **不引入 ORM / SQL 依赖**：DB 只是宿主的一种实现，`src/` 里仍只有 JSONL 与内存两种。
  Node 22+ 内置 `node:sqlite`，"CLI 自建 SQLite"在零依赖红线内可行——但那是**宿主的可选实现**，
  不是形状的一部分。
- **不要求存储提供自增 / 序列**：序号由写入方（引擎）分配、账本只播种（§1.3）。形状只要求
  "能按自然键排序"。
- **不把 `content` 拆到块一级**：原子单位是**消息**。
- **不做"无限保留历史原文"**：原文在账本里，上下文只放骨架。
- **不给白板加时间维度**：退场靠状态（done / 被推翻 / 被证伪），不靠"多久没用到"。
- **不在 `folds` 里存向量**：会话内它永远不会触发——200k 窗口下 10 折（约 6000 轮）全部能按完整
  description 放下；而跨库语义检索的索引是**宿主的职责**（键是项目/用户/折，引擎手里只有一 run 一个文件）。
  引擎侧也不能实现 embedding（零依赖）。形状对索引的唯一承诺是：**每一折都能被单独编码**（§3.4 ③）。

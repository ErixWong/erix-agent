## B. 对抗性攻击与本地探针

### B1. 重跑改告知

用临时目录调用 `createCliTools`/`wrapExecuteTool`，没有 provider：

- 同一实例的第三次相同命令 metadata 中确实有首次 `round: 8`、`artifactId: 002-exec.txt`、digest、locator 和 `status: "ok"`；两份正常输出为 `001`、`002`、`003`。
- 文本告知为“首次执行记录：second-secret（.../002-exec.txt）；工件状态：ok”，没有 round、digest、locator。它们只在结构化 metadata 中存在。
- 删除首次 txt 得到 `missing`；改写首次 txt 得到 `stale`；超过 `MAX_ARCHIVE_BYTES` 得到 `truncated`；把 archiveDir 指向普通文件使归档失败，重复执行得到 `unrecoverable`。这四类状态不是死代码。
- 首次/第二次输出中的 `token`、Bearer、GitHub/npm/private-key 等已知模式不会被 `firstSafeArtifactValue` 放入“首次记录”文本；但实际第二次命令的原始 tool output 仍会返回，不能声称重跑机制本身是凭据隔离层。
- **反证**：先用实例 A 写入 `outputs/001-exec.txt`，再用实例 B（同 cwd、同 archiveDir）执行相同命令。B 的重复 Map 为空，未出现重跑告知；它重新尝试 `001-exec.txt`，返回归档 `EEXIST`，也没有第二份可区分归档。这正是 CLI 显式 `--session`/跨进程 resume 会遇到的路径。

因此，重跑机制在单进程 happy path 可用，但发版断言必须限定“同一工具实例/本 run 生命周期”，或先修复持久化归档序列与首次索引。

### B2. bounded recall

使用 6 轮大记录和多轮 `limit: 2, maxBytes: 12`：

- 同一参数反复续取无重无漏；UTF-8 切片不超过 `maxBytes`，状态和 nextCursor 正常。
- 位置参数 `recall(runId, fromRound, toRound, pattern)` 仍返回旧字符串，包含 pattern 子串行为。
- 传入 `artifactRef: "does-not-exist"` 仍返回整个 run 的 `status: "ok"`，说明该字段没有被实现或拒绝。
- 先取 `maxBytes: 2` 得 cursor，再以 `maxBytes: 100` 续取，返回 `ok`/后半内容，而不是 `stale`/`cursor_mismatch`。代码的 `cursorShape` 只含 run/range/pattern/sourceVersion（`src/store/bounded-recall.js:140-155`），没有 limit、maxBytes 或 artifactRef。
- `maxBytes: 0` 返回 `status: "truncated"`、空 text 和指向同一 `fragmentIndex/byteOffset` 的 cursor；重复相同请求会继续得到空 truncated，调用方可能无限续取。
- 临时 JSONL 中写入约 5 MiB 的单条记录，再请求 `maxBytes: 64`，响应只有 64 bytes，但 `src/store/file.js:74-86` 的 `readRecords` 会先把整行累积到 `buffer` 再 `JSON.parse`。实测 RSS 增长约 17 MiB、耗时约 192 ms；所以这是输出有界，不是对超大单条记录的源头内存硬顶。
- `rangeStatus` 只有在范围长度不超过 100,000 时逐轮检查（`src/store/bounded-recall.js:67-83`）；更大范围中的内部缺口可被当成可恢复。

游标续取的核心 happy path 通过，但 API 设计稿和宿主契约要求的参数绑定、单条 item 上限、缺失语义没有完整落地。

### B3. run state

- 20,000 个不同 tool name 构造出的 `createDeterministicRunState`：渲染文本为 372 字符并有 `[run state truncated]` 标记，但 state 对象本身的 `deterministic.tools` 仍有 20,000 项，JSON 约 890,021 字符。`renderRunState` 的 400 字符上限不是持久化上限。
- 重复 `upsertRunStateInMessages` 会保留一个 marker，resume 测试通过，替换而非追加成立。
- `semanticStateProvider` 返回旧 version 会显示 `status=stale`；provider 抛错会显示 `error`，没有隐式调用模型。
- 语义文本是可选的模型/宿主语义内容，不是确定性事实。`safeText` 的 credential regex 不覆盖通用 `password=abc123`、所有 npm/JWT/数据库 URL 等形式；宿主返回的这类文本会被持久化和注入。当前实现不能承诺“run state 不含凭据”。
- 文件 store 的损坏 state JSON 会抛出 `SyntaxError`，不会静默吞掉；但 `{schemaVersion: 99, deterministic: {}}` 等缺字段/未知版本对象会被 `applyRestoredRunState` 接受，工具/计数等随后按默认值恢复，造成静默状态丢失。没有 `schemaVersion` 迁移、stale 标记或明确不可恢复结果。

### B4. ADR-013 guard 章程

- `bin/final-guard.js` 为 251 行，满足 ≤300 行。
- 本 diff 把归档读取校验移到新增的 `bin/final-guard-support.js`；`explicitAttributions` 只接受已知 label 的显式 `label=value`/“label 是 value”格式，来源匹配也只比较已知 key/path，未新增相似度、关键词猜测或语义判断。
- 新增的 `archiveIndex`/`boundedCommandSummary` 是折叠导航和脱敏展示，不参与 guard decision；属于源头导航，不是 guard 推断。
- `skipped` 在 loop、CLI metrics、契约和测试中都保持独立，不会转成 `verified`；无 label 的凭空值仍只能 skipped，符合 ADR-013 已知边界。

**裁决：ADR-013 合规，guard 本身不是本次 no-go 原因。**

### B5. 回归面与被放宽的断言

被修改/删除的重复命令断言集中在 `test/tools.test.js`、`test/notes-autocapture.test.js`：

- 旧的“重复命令被拦截”“非幂等重跑不返回第二值”“必须给 note_read 指针”改为“执行成功、出现第 N 次告知、metadata 有 `rerunOf`、两次归档”。这是用户明确要求的行为改变，方向合理。
- 新测试保留了 missing/stale、归档失败、wrapped command、合法第二 UUID、replayable rerun 和计数递增覆盖；但没有跨进程/archive sequence 测试，正好遗漏 B1。
- credential 测试从“重跑结果不包含 secret-value”改成只检查告知第一行和 `rerunOf` 不含该值，同时允许 `second.data` 含真实第二次命令输出。这对“执行照常完成”是合理改写，但覆盖面比旧测试窄，不能作为全面凭据不泄漏证明。

其它相关断言变化：

- `test/loop-termination.test.js`、`test/app-container-p0.test.js`、`test/loop.test.js` 把 max-round/stall/continuation 的额外 provider 请求和 `forcedFinal` 纳入预期，符合新机制。
- `test/loop-final-guard.test.js`、`test/notes-final-guard.test.js` 新增 `skipped !== verified`、默认关闭和显式开启断言，符合契约。
- `test/compact/*` 增加 stub 脱敏、navigation 10/400 上限、替换而非膨胀；`test/run-state.test.js` 覆盖渲染上限和 resume marker，但没有检查持久化 JSON 的总大小、未知 schema 或 semantic 凭据。
- notes 测试覆盖 relevance/filter/sort 和 skill wiring；没有发现把 EMPTY/null 边界改成成功形状的断言。旧位置 recall 的空范围仍返回空字符串，新的对象 API 才返回机器状态。

### B6. 宿主影响

1. **verification**：默认 loop 返回 `verification.status: "skipped"`；它不是失败，但也绝不是 verified。CLI 对 skipped 退出 0，宿主必须读取字段而不能只看退出码。
2. **runToolLoop**：新增 `runState`、`resume`、`todoStateProvider`、`semanticStateProvider`、强制收尾相关默认值；`finalGuard` 库注入语义保留。宿主若只实现 `markRunState` 而没有 `saveRunState/loadRunState`，不会得到持久 run state，且这是静默能力降级。
3. **TranscriptStore**：新增 `saveRunState/loadRunState` 和对象式 recall；旧位置参数保留。契约文档宣称的 `artifactRef`、严格 cursor 绑定、超大 item hard cap 当前不成立。
4. **notes/skills**：`skills/` 随包发布，CLI 默认发现 notes，`--no-notes` 仍只排除 notes；`note_list` 排序从旧时间顺序变为 relevance 优先，旧宿主不得依赖顺序。
5. **CLI**：`--final-guard` 新增 opt-in，环境变量也可开启；`--no-final-guard` 不覆盖环境变量。显式 session 的跨进程 resume 是当前 archive collision 的触发面。
6. **文件/状态生命周期**：发布包 `files` 包含 `src`、`bin`、`skills`、契约文档和 contract tests（`package.json:12-20`），但不包含全部 `docs/decisions`；需要 ADR 的宿主不能假设 npm tarball 含完整决策文档。

## C. 发布裁决

### 阻塞项（按严重度）

#### P0 — resume/跨进程归档不具备可审计的 rerun 语义

- **现象**：新建 `createCliTools` 实例重用同一 archiveDir 时，`archiveSequence` 从 0 重置，重复命令 Map 为空；第一次归档占用 `001-exec.txt`，下一次写 `001-exec.txt` 得 `EEXIST`，没有 `rerunOf`，也没有独立第二归档。
- **证据**：`bin/tools.js:620-630` 的 sequence/Map 是实例变量；`bin/tools.js:801-850` 没有扫描已有归档或恢复 sequence；B1 探针复现跨实例 `crossProcessNotice=false` 和 archive failure。
- **影响**：CLI 显式 session、REPL/宿主重启、无人值守 resume 会破坏 CHANGELOG/消费者契约承诺，历史工件无法按首次 round/digest/locator 对账；重复执行虽发生，消费者却看不到完整事实。
- **最小修复方向**：以持久化 run/archive index 或安全的单调 artifact id 初始化 sequence，并在新实例启动时按 normalized command hydrate 首次 artifact；归档失败/冲突要显式返回状态，不得复用旧路径。
- **验收方式**：两个独立 `createCliTools`/两个 CLI 进程共享同一 run 目录，第二次相同命令必须生成可读的 `002`，返回 `rerunOf` 指向 `001` 的 round/digest/locator；恢复后第三次仍为独立序号，归档目录无覆盖/碰撞。

#### P1 — bounded recall 没有兑现契约的参数、缺失和源头内存上限

- **现象**：`artifactRef` 被忽略；cursor 不绑定 `limit`/`maxBytes`/artifactRef；`maxBytes: 0` 可产生空输出的重复 cursor；大于 100,000 轮的内部缺口不检查；文件 store 先整行读入超大 JSONL。
- **证据**：`src/store/bounded-recall.js:140-155` 的 cursorShape 缺字段，`108-117` 也没有 artifactRef；`209-219` 的 zero-cap 路径；`src/store/file.js:74-86` 的整行 buffer/JSON.parse；B2 探针得到 artifactRef 仍 `ok`、改变 maxBytes 仍可续取、5 MiB 单行导致 RSS 增长约 17 MiB。
- **影响**：宿主可能把错误 artifact 当作目标、改变预算后从错误位置续取、无限重试空页，或以为 `maxBytes` 是内存硬顶而遭受单条记录内存峰值；范围缺口可能被误报为可恢复。
- **最小修复方向**：实现或明确拒绝 artifactRef；把所有影响结果的规范化参数纳入不透明 cursor；zero-cap 返回可终止状态；改为记录/块级流式解析或对单 item 明确 `item_too_large`；任何无法证明完整的范围都返回 `unrecoverable`/`error`。
- **验收方式**：参数任一变化得到 `cursor_mismatch`/`stale`；artifactRef 只返回目标；zero-cap 不产生不可推进 cursor；超大单条记录的读取内存由硬顶控制；构造 >100,000 轮带缺口的范围必须非 `ok`；旧位置参数及 pattern 断言保持原样。

#### P1 — run state 持久化无界，且旧/未知 schema 可静默丢状态

- **现象**：渲染注入≤400并不等于持久对象有界；不同工具名可把 `deterministic.tools` 无限扩大。未知 schema/缺字段 state 被接受并恢复默认计数。
- **证据**：`src/run-state.js:26-44` 的 `normalizeCountMap` 无 slice，`115-151` 直接保存完整 tools；`src/loop.js:1106-1128` 没有 schema/version reject；B3 20,000 工具得到 JSON 约 890,021 字符，未知 schema 恢复为 schema 1、stateVersion 0、空 tools。
- **影响**：store 文件/数据库和每轮 append 的 state 可能膨胀，违背“有界 run state”；升级、损坏或宿主旧 state 可能把工具足迹/预算/错误计数静默重置，resume 后行为不可审计。
- **最小修复方向**：对持久化 deterministic state 和 rendered state 使用同一明确上限，截断后在对象中写结构化 marker/count；严格校验 `schemaVersion`，旧版本走显式迁移，未知/缺字段返回 `stale`/`unrecoverable` 或可观察错误；损坏 JSON 保持 fail-closed。
- **验收方式**：100k 工具名、1000 文件、超长 todo/semantic 的持久 JSON 仍有可测硬顶并有标注；旧/未知/缺字段/损坏 state 均有明确结果而不静默归零；resume 重复执行不增加 state 大小或 marker。

### 非阻塞项（可发前记录，但本次 no-go 仍成立）

- 文本重跑告知没有 round/digest/locator，只有结构化 metadata 有；文档应写“metadata 附带”，不要暗示文本完整展示。
- `semanticStateProvider` 的文本属于宿主注入的 derived 内容，当前过滤器不能保证通用凭据脱敏；宿主应自行清洗，或后续将 credential policy 变成可观察的显式协议。
- navigation record 的 400 是 JSON 字符数目标，不是 UTF-8 envelope 字节硬顶，也没有 source version；应在消费者契约中明确只是导航。
- `skipped` 的 CLI exit 0 容易被 shell consumer 误当成功；README/CHANGELOG 应把“必须读取 verification.status”放在 flag 迁移提示旁。
- note_list 的 relevance 优先排序是有意行为变化，但应在迁移说明中提醒依赖旧时间顺序的宿主。
- `docs/design/2026-09-14-bounded-recall-api.md` 仍标为“设计稿（不实现）”，应更新为实现状态或明确哪些设计项仍未落地。

## 2. 自研 agent 的决策树（跨项目提炼）

**Q1：长会话下，上下文里丢掉的工具输出还需要被找回吗？**
- 需要 → 走**无损召回派**：压缩只改「进入上下文的路径」；原文落 DB/文件；给专用召回工具（要求：分段预算 + 不透明游标 + 机器可辨状态）**或**稳定暴露原文路径（pi 的 `PI_SESSION_FILE` 模式）。阈值可以激进（hm 50%）。
- 不需要 → 走**有损摘要派**（cx 默认）：阈值要靠后（90%），并把「尽量新开线程」写进给用户的提示。
- 混合 → 至少保证「非幂等命令的捕获」可召回（ex 的 `auto-capture` + pinned note 就是这个思路）。

**Q2：你的 system prompt 有多长、每轮有多少动态内容？**
- 长且多轮 → **必须**把 prompt 缓存当不变量：分层（stable/context/volatile）、动态内容走 user 消息或工具结果、外部状态会话级冻结、稳定 id。参考 hm 与 cx。
- 短或一次性任务 → 不必投入，直接拼字符串（pi 的做法）。

**Q3：工具池有多大？**
- < 10 个 → 全量注入（pi）。
- 10~40 个且单轮只用几个 → 工具搜索 + 三级清单退化（hm）或 `ToolExposure` 六值（cx）。
- 来自多个 MCP server → 单代理工具收敛（ex），或 `mcp__server__tool` + 搜索（cx/hm）。
- 多且都要精确调用 → 不要只靠清单，模型会用可见工具绕过（hm 实测）。

**Q4：多用户吗？**
- 单用户本地 → 「一 home 一用户」最简单（pi/cx）。
- 服务端多租户 → 必须有字段级隔离键（tw 的 `user_id × expert_id`），或一租户一实例（hm 的 profile + 外部 provider）；**不要**指望「一个 prompt 里塞多用户记忆」。

**Q5：记忆怎么写？**
- 一律：**主循环少写、冷路径整理**。可选形态——后台 review fork（hm）、两阶段后台流水线 + workspace diff（cx）、run 结束 janitor（ex）、业务压缩顺带（tw）。
- 注入一律用**冻结快照**（hm），避免「刚写的记忆改变本轮 prompt」导致缓存击穿与不可复现。

## 3. 不要抄的反模式（都有实证）

1. **让 LLM 复述精确标识**（PR 号 / SHA / 路径 / 错误串）：任何「让模型复述精确值」的方案都会丢东西 —— 用正则机械抽取（hm）。
2. **静默截断**：cx 的 `project_doc_max_bytes` 超限只 warn；hm 的截断 marker 里直接给原文 `read_file` 路径。截断必须能被模型自愈。
3. **指向残缺归档**：落盘必须做无损校验（hm 的字节比对 + `wc -c` 往返），校验不过就删档退回内联截断 —— 「指向一个残缺文件」比直接截断更糟。
4. **每轮变化的内容放在 system prompt 头部**（tw 的时间戳）：长 prompt + 前缀缓存 = 每轮全量重算。
5. **同一语义的折叠机制并存**（tw 的 Topic 压缩 / AgentLoop compactor / Psyche 三者）：排查「模型为什么忘了」要跨三处读日志；本项目若加 L2/L3 记忆，必须先把边界写清（`chat-memory-boundaries.md` 就是 tw 自己补的）。
6. **全量注入且无任何税率**（tw 的工具面）：工具数量的成本是线性的，且会带来「选错工具」的概率上升。
7. **压缩后的提示语只告知状态、不给出动作**（cx 的 `Warning: truncated output`）：把信息丢失转译成动作是关键（pi 给的 `sed` 命令、tw 给的 recall 调用、ex 给的配方）。
8. **就地写历史且期望缓存命中**（ex 自己的取舍）：如果依赖 prompt caching，折叠产物必须挂在稳定前缀之外。

## 4. 建议的验证实验（本项目可执行）

1. **recall 命中率**：构造一个 40+ 轮任务，其中第 5 轮输出一个随机 token（如 `VALUE-7f3a9c`）；在第 35 轮提问该 token。对比三条路径：默认折叠（有 recall）vs `recall:false`（无 recall）vs 不折叠（基线）。指标 = 命中率 + 总 token + 轮数。
2. **压缩后「继续动手」能力**：把「已改文件清单」作为判据——验证 `导航记录` 与 `fold-llm` 的「已改文件」节是否足以往后继续（对比 pi 的文件账本思路）。
3. **多次折叠的稳定性**：连续触发 ≥5 次折叠，断言摘要块不堆叠、`foldedThrough` 单调、`recall` 水位线描述准确。
4. **`--agent erix|pi` 横向对照**（erix-bench 已有能力）：同一任务、同一模型，比较 `judge.log` 里的折叠次数、recall 调用次数与最终完成度。

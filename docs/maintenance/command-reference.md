# Command reference — the cold half of `AGENTS.md` §3 and §4

> Chinese version: [command-reference_cn.md](command-reference_cn.md)

`AGENTS.md` is the instruction face: it is injected into every session and executed without verification, so it
carries only what every task has to obey, and its size is budgeted by `npm run check:agents-directives` (issue
#726). This page is the other half — the reference material behind each gate, which you read **when you are about
to touch that gate** and not before.

Every block below was moved out of `AGENTS.md` **verbatim** in issue #726 (the §3 command-table explanations and
the long notes that used to sit under it, plus the §4 paragraphs named in the pointers there). Nothing was
rewritten, and no discipline sentence was moved: the red lines, the release discipline, the git boundary and the
environment/model rules stay on the instruction face. The headings are the anchors the instruction face points at
(`#check-docs`, `#type-ratchets`, `#docs-anchors`, …), so a pointer from `AGENTS.md` lands on the section that
explains that gate.

## check-test-summary
**Suite-summary reconciliation** (issue #301): `scripts/suite-summary-reconcile.mjs` reads the TAP summary a finished `node --test --test-reporter=tap` run printed (issue #774 names the reporter in argv instead of inheriting it, because node 24 changed the default to spec; the counters themselves are the same set either way — `# tests` / `# pass` / `# fail` / `# skipped`, plus the sibling counters `node --test` prints beside them) out of a captured log (`--log <file>`, or `-` for stdin) and reconciles it against `test/test-suite-baseline.json`, printing a fixed-prefix `TEST-SUMMARY …` line plus `TEST-SUMMARY-VERDICT ok|red` and appending both to `$GITHUB_STEP_SUMMARY` when that variable is set. Red (exit 1, naming the delta): `tests` **below** the registered value (a dropped case is the accident — running *more* cases than registered stays green and adds a `TEST-SUMMARY-HINT` line naming the value the registry could be raised to, since raising it is still a human action), `fail` not equal to the registered value, `skipped` above the registered ceiling, or a summary whose own fields do not add up (`pass` / `fail` / `cancelled` / `skipped` plus the sibling counters must sum to `tests`). A log with no complete summary block exits 2 — "did not read it" is never "no problem". A log whose shape is recognized as the **spec** reporter (Node 24's default for `node --test`: `ℹ tests …`) gets its own verdict code `NOT_TAP_LOG`, still exit 2: undetermined, never green, and never reported as a regression — comparing spec numbers against a TAP-registered baseline would turn a runner-version change into "missing test cases" (issue #774; what keeps CI's log TAP-shaped is that `package.json`'s `test` script names `--test-reporter=tap` in argv instead of inheriting the runner default). Alongside that undetermined verdict the script also prints a `TEST-SUMMARY-SPEC tests=… pass=… fail=… skipped=…` **observation** line (issue #781): it reports the numbers it read but does **not** judge — it is not fed to the reconciliation, does not change the exit code (still exit 2), and deliberately does **not** carry the `VERDICT` / `EXPECTED` suffixes, so a reader who greps `^TEST-SUMMARY-VERDICT` still counts exactly one line (the undetermined verdict) and never reads this observation as a verdict; the guard for that is a self-test case, not prose. The registered file is an **expectation, not a measurement**: the truth is what the command prints on that run and it varies by environment (real-upstream gate open or not, pi loader installed or not, both move `skipped`), so the ceiling is the largest environment measured so far and skipping fewer cases stays green. There is no `--sync` for that file on purpose: raising the registered value stays a human action, and a run that happens to print fewer cases must never be able to launder itself into a new baseline. The tests are never changed to match the numbers either. `--print` shows the registered expectation plus the recorded `observations` without judging anything, and `-- --self-test` is the gate's own reverse proof (synthetic TAP fixtures and registries, plus the CI wiring: the `Test suite` step tees with `pipefail`, both new steps exist, and this command points at the script)

## check-changelog
**CHANGELOG coverage of public-surface merges** (issue #691 — the gate issue #636 predicted): `scripts/changelog-coverage-check.mjs` answers the question every other CHANGELOG gate skips — *should there be an entry at all*. Both the range and the section are read out of the tree, never off a hand-kept list: the version under test is the newest `## [x.y.z]` section of `CHANGELOG.md` (`--version` overrides it), the range is the greatest tag below that version `..` that version's own tag (or `HEAD` while the version is untagged), and the merge set is `git log --first-parent --merges`. A merge counts as **behaviour-visible** when its first-parent diff (`git diff --name-only <merge>^1 <merge>`) touches a public-surface path — `src/`, `bin/`, `package.json`, both READMEs, the host-consumer contract, the requirements files, or the current version's upgrade guide; a merge that only touches tests, internal docs, `scripts/`, delivery notes, `AGENTS*`, CI config or examples is a **category exemption decided by rule, not by register**. Coverage is checked in **one direction only** — every public-surface merge number must appear in that version's CHANGELOG section or in a registered exemption — because prose that cites an older issue is legitimate and the reverse direction would red on it. Red names the issue number, the merge's short sha and the public files it touched. `COVERAGE_EXEMPTIONS` exists for the reverse case only (a change that looks category-exempt but is behaviour-visible): every row needs a `why`, an idle row is red, an empty `why` is red, and the row count is reconciled against `COVERAGE_EXEMPTION_MAX` in both directions. An endpoint that does not resolve, a section that cannot be read, or git being unusable exits 2 rather than passing. `node scripts/changelog-coverage-check.mjs --self-test` is the gate's own reverse proof on a synthetic git repository built in `os.tmpdir()` (its own tags, branches and merges — never this repository's history), and it also checks the wiring itself: the blocking CI step sits between `check:test-summary` and `check:docs`, the checkout fetches full history, and the npm script points at that file. **Who writes the entry (issue #702)**: the PR that touches the public surface puts **its own** issue number into the current version's CHANGELOG section, in that same PR. What the gate compares is the **number** — the section body and the merge subject go through the same reader, and an entry is never required to carry a merge sha (the sha of a merge that has not happened yet is not knowable, so a rule demanding it would be red against every PR including itself). Writing `#702` in the entry is therefore enough and the sha can be added later; forgetting the number goes red on `main`, and that red is the enforcement doing its job, not a bug and not a row for `COVERAGE_EXEMPTIONS` (which exists only for the reverse case: behaviour-visible yet category-exempt). `npm run release:day -- --stage preflight` runs this gate as step 1 with no waiver

## docs-anchors
Reverse-proof self-test of the list/unit/enum anchors (issue #210): change one doc claim → red, change the source truth → red, change nothing → green; a mutation that stops applying also fails (issue #210 R2) **Since issue #302 the tree it runs in does not change the verdict**: the two `#280` tree-shape cases run on a **synthetic tree fixture**, so the result no longer depends on whether this machine's untracked `docs/tasks/` directory (never committed) exists — the three shapes (no / empty / filled `docs/tasks/`) are each run on a `git archive HEAD | tar -x` checkout, and the command prints its own case count and red count (neither number is copied here). Before #302 it was the other way round: 3 of the cases were known false reds in a checkout without `docs/tasks/` (5 with an empty one), tracked in issue #281 — those reds are gone, so "run it in the development tree" is history, not a current requirement.
- Anchor granularity (issue #210): **do not assume "delete one mention in the docs turns red"** — most anchors are
  *existence-level* (the whole `defaults` group, `modulemap`, `paths`: they ask "is this string present in that file",
  so deleting one extra mention of the same value stays green). Only these are *per-occurrence* (each declaration site
  is compared on its own, so missing / extra / renamed members all go red): the `version` claims, the README
  `files`/`exports` fences — compared **bidirectionally** with `package.json`, so renaming or dropping a key in the doc
  is red, not just adding one — and the list/unit/enum anchors (file-tool list, CLI tool list, vendor skip directories,
  `formatSize` unit tiers plus every `` `bytes` → `rendered` `` example claim, built-in compaction strategy names), plus the
  `cli-flags` anchor (issue #391 R4: the flag set of the `erix chat` / `erix repl` usage lines is compared **both ways**
  against `bin/cli.js`'s help text, so a flag added to the help and forgotten in the READMEs is red — and so is one the
  README invents; aliases like `-c|--continue` and `--no-final-guard` are counted, and its exemption register must stay
  empty-or-justified, since an idle entry is itself red).
  Those anchors also reconcile the **number of declaration sites between the EN and the CN doc**, which is what catches
  "someone deleted the whole sentence on one side". Every per-occurrence rule carries its reverse proof in
  `node scripts/docs-drift-check.mjs --self-test`; run it after touching `scripts/docs-drift-check.mjs`. The level of
  every anchor, and why the remaining ones were *not* upgraded, is listed in the header comment of that script.
- Doc line anchors (issue #286, first batch T-a): docs must not lean on **bare line numbers**. `paths` used to strip
  `:1234` before resolving a reference, so only the file was ever checked — a line number that drifted into another
  function, or past the end of the file, stayed green (the contract pointed at line 398 of `src/store/notes.js`, a file that is 383 lines long). Three anchors now hold that line, all wired into `--self-test`:
  *`symbol-anchor`* is *per-occurrence*: every `` `symbol` (`path`) `` or `[symbol](path)` reference must find a real
  declaration of that symbol **in that file** (`function` / `class` / `const|let|var` binding / destructuring /
  re-export / method / object key / `process.env.X`). Extraction reads the **code** face only: comments and
  string literals are masked out first, so a name that appears only inside a comment or a quoted string is *not*
  a declaration (issue #299 — before that fix, `const X = 1;` written inside a block comment "proved" X was
  declared, and a quoted name in a comment fed the weak literal tier). A missing symbol is red and the message names the nearest
  symbols actually declared there; a file from which no declaration can be extracted at all is red too (#164:
  no silent pass when ground truth cannot be read). Named string *values* — termination reasons, provider error
  codes — are the one weaker tier and are accepted only in the five files listed with a reason in
  `SYMBOL_VALUE_MEMBERSHIP` in `scripts/docs-drift-check.mjs` (the fifth, `bin/final-guard.js`, was
  added for issue #743 so the CLI guard's two skip reasons are actually checked). Because the bare-line ratchet keys on
  (document, target file, line range) — **never on the doc's own line number** — rewriting
  `` `symbol` (`path:1517-1531`) `` into a bare `path:1517-1531` leaves that count untouched while deleting the
  symbol check entirely, so `symbols` carries its own **only-up floor** `SYMBOL_ANCHOR_MIN_UNIQUE = 243`:
  dropping below it is red — that is the degeneration being caught, not a ratchet rise — and exceeding it earns a "raise the floor" note.
  Both numbers are read back out of the script's own text, which is what lets `--self-test` prove they are locks.
  The measurement log that used to sit in this parenthetical — every past reading, merge by merge, with the tree
  it came from — now lives in `docs/maintenance/symbol-anchor-ledger.md`. That file is history, not current state;
  nothing on this page restates it.
  *`symbol-anchor-span`* (#286 batch T-b1a) is the *per-occurrence* companion of the rule above: when a symbol anchor
  **carries a line range** — `` `symbol` (`path:1517-1531`) `` — that range must **intersect that symbol's own ground
  truth in the referenced file** (`lo <= p <= hi`). Ground truth = every declaration site of the name (not only the
  first: `sideEffect` legitimately appears both in the persistence normalizer and in `fail()`) plus, in the four
  membership files, the lines where that named string value occurs. A range pointing elsewhere is exactly the #286

  before resolving. Two legal fixes: **drop the range** (`` `symbol` (`path`) ``, preferred: numbers drift and

## release-day
**The release day as one command, minus the half only a human can do** (issue #689, written after 0.30.0 went out with a stale release state): `scripts/release-day.mjs` walks the day in four stages. `--stage preflight` is the §4 checklist in order — `check:changelog` → the `[Unreleased]` carry step (issue #715, an in-process reading rather than a spawned script: **red** when this version's section is open and entries are still parked under `## [Unreleased]`, **not judged** when the carry cannot be read because the version has no section yet or that section already carries a release date, **green** only when the section is open and `## [Unreleased]` is empty) → `check:docs` → `check:docs:strict` → `ERIX_E2E_REAL=1 check:release:real` → `check:release` → `check:host-consumers -- --hosts …` — stopping at the first red and naming which step it was, and reporting a gated step that did not run as **not judged** (exit 2) instead of green, so a missing `ERIX_E2E_REAL` or a `--hosts` directory that is not there can never look like a pass. `--stage publish` **does not fork `npm publish`**: the device-flow scan is the human half, so it prints the pitfalls that have bitten this repository (npm 12 lives at `~/.npm-global/bin/npm` and is shadowed by `/usr/bin/npm`, every publish needs its own device flow, a non-TTY URL is masked, ENTER kills npm, the registry lags after the `+ erix-agent@<ver>` line) and exits 3; `--publish-cmd` is an explicit opt-in that is off by default. `--stage writeback --version <x> --published <x>` is **the discipline this ticket is about**: after a successful publish the release state is written back *before* the tag — `scripts/docs-drift-check.mjs --sync` rewrites only the release-state sentences (the current-version claims in both READMEs, both requirements files and both AGENTS files, plus the current CHANGELOG section's heading — the `（未发布 / unpublished）` marker **and** the release date, written in the same step because they are two halves of the same fact: `--published-date <YYYY-MM-DD>` defaults to today in UTC+8) and leaves every other byte alone; the writeback is then committed and `check:docs` is re-run immediately as the proof that it is self-consistent. That re-run happens **before** the tag exists, so its `check:docs` answers exit 2 with `TAG_MISSING` — the date↔tag half has no truth yet; that is **not judged**, never red, and only when every not-judged reason is `TAG_MISSING` (any other unreadable truth stays red, and `finalize` re-runs the gate with the tag in place). `--stage finalize` clears `src/**/*.d.ts`, creates the annotated tag `v<version>` pointing at the **version-cut commit** (the commit `git blame` reports for the `package.json` `version` line — never the writeback commit), pushes `main` and the tag through `git push origin` (GitHub + Gitea, never `--force`: main is protected), verifies **both** remote URLs with `git ls-remote` and reds when the two sides disagree, then runs `check:docs` / `check:docs:strict` again. `--all` walks the stages in order and **resumes from the state file** (`$RUNNER_TEMP`/temp dir, never committed): a `phase=published_unwritten` entry — written the moment the writeback starts — means "published, not written back", so a rerun continues at the writeback and never re-publishes, and `finalize` refuses unless the state says `phase=written` and the worktree is clean, so a tag can never go out while the docs still say unpublished. `--dry` writes nothing, publishes nothing, tags nothing and pushes nothing. `node scripts/release-day.mjs --self-test` is the offline reverse proof on synthetic trees and fake runners (a red step stops and is named, a closed gate is not judged, a failed writeback leaves the resumable state, finalize without a writeback is red, two disagreeing remotes are red, `--dry` writes not one byte, a `check:docs` exit 2 is not judged only when every reason is `TAG_MISSING`, and `--sync` touches only the release-state sentences — a hand-moved boundary reds); the case count is printed by the command

## check-agents-directives
**Blocking gate** (issue #642) for the **instruction face** — `AGENTS.md` / `AGENTS_cn.md`, the page every session injects and executes without verification. `scripts/agents-directive-scan.mjs --strict` reds three classes of variables that live elsewhere and expire: a work-order status claim (a ticket number plus a status word), an expiring measurement copy (a measurement verb plus a number), and a bare source coordinate (a `src/…js` path carrying a line number). Pre-existing hits are held as per-file per-class ceilings — a ratchet, so cleaning them up is a pass with a "you may lower the ceiling to N" hint, a new hit is red, and a ceiling left with no hits is red too. The ceilings themselves are **derived state**: `--sync <file>` is the only legal way to change one (it rewrites the digits from the live measurement and leaves every reason comment alone), and `--verify <file>` reds on any cell that is not equal to that measurement — so a hand-copied ceiling is red in both directions, high or low, and the CI step runs both. **Byte budget (issue #726 — the one block on this page that was *not* moved out of `AGENTS.md`).** The instruction face is part of the system prompt and folding does not touch it, so every byte here is re-sent on **every** turn; issue #726 therefore made length itself a criterion, judged as criterion ⑥ of `--strict`. The budget is **derived state, never a hand-written number**: `budgetFor(measured) = ceil512(measured) + 1024`, i.e. the measured byte count rounded up to the next 512-byte boundary plus a 1,024-byte headroom (total headroom ≤ 512 + 1,024 = 1,536 bytes, deliberately under 2,048: headroom is "how much this page may grow without going red", and a few kilobytes of it would turn the criterion into decoration). `--sync <file>` is the **only** legal way to change a cell — it writes exactly `budgetFor(measured)` and leaves every reason comment alone. `--verify <file>` reds on **any** cell that is not equal to that derived value, so a hand-copied budget is red in both directions, too high and too low, and the CI step runs `--strict` and `--verify` both. `--strict` itself is the ratchet: measured > budget ⇒ red, naming the measured bytes, the budget and the overflow (tokens folded at **3.4 bytes/token** — a 2026-11-05 relay measurement that is *not* a constant and is used for reporting only, never for judging); measured ≤ budget ⇒ green, which is exactly what the headroom is for. An **idle** cell is red on the same convention as the ceilings above: a budget row whose file has left the instruction face (a dead entry), or a budget written as 0 (a cell that can never hold). The remedy for a real overflow is to move reference material onto this page, not to raise the budget; raising it needs a reason in the report and still only happens through `--sync`.

## gate-reproducibility
- Gate reproducibility (issue #280): `npm run check:docs` and `npm run check:docs:strict` must exit 0 both in a development worktree and on a **fresh clone** (`git archive HEAD | tar -x -C <empty dir>`). The “local archive” class — files under `docs/tasks/`, a directory that is gitignored on purpose and therefore absent in any clone — is adjudicated by its **declaration** (an entry in `LOCAL_ARCHIVE_REFS`, or an in-line statement next to the reference); the physical file is verified only as a bonus when that directory happens to exist, and its absence never turns the gate red. The gates that genuinely have a local prerequisite are the ones that need `node_modules` — the two dev packages `typescript` + `@types/node` (issue #213): `npm run check:inventory` (it parses every scanned test file with the TypeScript AST), `npm run check:types`, `npm run check:types:strict` and `npm run check:types-build` (all three drive `tsc`), and `npm run check:pack-links` / `npm run check:release` (they shell out to `npm pack`, whose `prepack` hook regenerates the declarations, plus `tsc`). No other gate reads the toolchain.
- **Concurrent judgment (issue #799)**: never read `npm run check:docs`, `npm run check:docs:strict` or `node scripts/docs-drift-check.mjs` while `npm test` is still running in the same tree. Measured twice on one **committed** tree: with the suite in flight the command exited **0** and reported zero findings; the same tree, rerun after the suite had exited, exited **1** naming 20 drift items (`bare-lines` above its ratchet baseline, plus `cell-axes-anchors` read-column mismatches in both contract languages). After the drift was actually fixed, both shapes came back green — so the red was real and the green was the lie. This is the **silent-success** shape of failure: the exit code is exactly what the next reader consumes, and the wrong answer is the reassuring one, so "be careful" is not a control. **CI is not affected** (its steps are serial, see `ci`); only a local shell that overlaps a suite run triggers it. Until the attribution lands the ruling is procedural: **let the suite exit, then rerun, and treat only the clean run as the judgment** — a scan that overlaps another writer is *undetermined*, not a pass (the same rule issue #511 applies to a closed gate: not running is not a pass). Attribution is open in #799; the lead that the scan surface may pick up `src/**/*.d.ts` files that a suite member generates and deletes mid-flight is **a lead, not a finding** — whoever verifies it writes it here, and nobody copies it forward as fact.

## npm-policy
- ✅ **The only path (`npm@12`)**:
  ```bash
  npm i -g npm@12                    # 升级（系统 npm 10 不支持新流程）
  npm login --auth-type=web          # 浏览器 OAuth + passkey
  ```

- **Publish interaction (verified in 2026-09)**: even after `npm login`, `npm publish` still triggers **a separate device flow authentication** (EOTP; each publish requires authentication again, rather than being covered by login) — the terminal prints `https://www.npmjs.com/auth/cli/<id>`; copy it into a browser, scan/confirm the passkey with a phone camera, and the command line continues automatically.

## pitfall-4
4. For the no-browser + non-TTY authentication flow (verified in 2026-09, on a machine without a desktop): wrap npm with Python pty (`pty.fork()` + `select` to read output), use `setsid nohup` to fully detach from the process group so the bash tool cannot clean it up; use a regex in the script to extract the auth URL into a file, then read the URL and pass it to the user for browser interaction; **do not press ENTER automatically** (see above). Successful login writes the token to `~/.npmrc`; successful publishing is marked by the log line `+ erix-agent@<ver>`; reference implementation `/tmp/npm-pty-login5.py`.

## pitfall-5
5. **Auth URL regex gotcha (0.7.0 postmortem)**: login prints `https://www.npmjs.com/login?next=/login/cli/<uuid>` and publish prints `https://www.npmjs.com/auth/cli/<uuid>` — a regex like `npmjs.com/(login|auth/cli)/<uuid>` matches NEITHER. Use `npmjs\.com/\S*<uuid>`.

## pitfall-6
6. **Auth URLs expire in minutes**: surface the URL to the user in the SAME message where it was captured (never a later turn); each `npm publish` requires its own fresh device-flow auth, and each session can be used exactly once — an aborted run invalidates its URL, always re-issue.

## pitfall-7
7. **Publish success ≠ registry availability**: after the `+ erix-agent@<ver>` success line, npm prints `Your package is being processed and may take a few minutes to become available` — the registry can lag minutes; poll `https://registry.npmjs.org/<pkg>` before declaring failure.

## pitfall-8
8. **Right after publishing, `npm i -g` hits stale cached metadata** (ETARGET / old version): install with `--prefer-online` or pin the exact version.

## pitfall-9
9. **npm 12 lives at `~/.npm-global/bin/npm` and is shadowed by `/usr/bin/npm` (10.x)** in default PATH — invoke it by absolute path in scripts, or a 404/401 PUT will mislead you into diagnosing the wrong layer.

## pitfall-10
10. **Stale token → publish PUT 404 (2026-09-30, 0.13.0)**: an expired `~/.npmrc` token makes `npm publish` fail with E404 on the PUT (misleading); `npm whoami` returning E401 is the ground truth. Re-run `npm login --auth-type=web` (pty URL capture per pitfall 4), then publish.

## pitfall-11
11. **npm 12 publish PUT returns 202 Accepted (async processing, 2026-09-30)**: the `+ erix-agent@<ver>` success line prints BEFORE the package is visible on the registry (~2 min lag observed). Poll `npm view <pkg> version --prefer-online` for a few minutes before declaring failure (extends pitfall 7).

## pitfall-12
12. **npm publish triggers its own device-flow auth EVERY time (2026 policy) — including after a fresh `npm login`**; the publish URL (`npmjs.com/auth/cli/<uuid>`) must be captured via pty in headless environments and surfaced to the user immediately (see pitfall 4/6).

## pitfall-2

## pitfall-3

## publish-prerequisites

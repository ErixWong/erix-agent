# Notes 归因实验：模型为什么不主动查证

运行时间：2026-09-13T03:16:22.338Z。这是库级 `runToolLoop` harness，不调用 CLI 二进制。

> **样本量更正（2026-09-13 人工复核）**：本轮（stage 1）实际为**每个变体、每个模型各 1 次运行**（共 14 runs），而非 5 次——脚本首次调用因 180s 超时中断，重跑使用了 `--runs 1`。**所有比例均为 n=1/cell，只能作为方向性证据**；stage 2（n≥5，含新增 V7 值模式）待跑。
> 本文末尾的「补充分析（人工复核）」一节为本轮**最重要的发现**，请优先阅读——它修正了机器结论的归因优先级。

## 假设与可证伪判据

- **H1 不知道有这工具**：工具确实在 request.tools 中，但模型从未感知或无法把“需要历史值”与它关联。若 V0 的工具 schema 已发送而 V5 仍不调用 notes，或工具调用率与工具是否存在无关，则支持 H1；若 V5 显著调用则否定“完全不知道”。
- **H2 不觉得自己缺信息（记忆错觉）**：模型以为自己记得而直接作答。可证伪判据是终稿时真值已不在发给模型的 `messages` 中（`value_in_context_at_answer=false)，但仍输出具体值，并伴随“记得/之前/第一次”等来源声明；若值仍在上下文，不能归因于记忆错觉。
- **H3 触发条件太弱**：抽象的“需要时先查证”不足以产生前置动作。若 V1/V2 相比 V0 的 `note_call` 率明显上升，且 V5 也能调用，支持 H3。
- **H4 更便宜的路存在**：重跑命令或读归档比调新工具更符合习惯。若 V0 的 `archive_read` 或 `rerun_command` 显著高于 `note_call)，而禁用归档 V4 后 notes 上升，支持 H4。
- **H5 工具形态不吸引**：英文短描述、JSON 返回和陌生名字降低使用率。若只把描述改为中文并说明 when-to-use/重跑取舍的 V3 相比 V0 上升，支持 H5。
- **H6 能力/习惯问题**：即使被明确要求也做不到。若 V5 或 V6 在工具存在且任务可完成时仍不调用 notes，支持 H6；若 V5/V6 能稳定调用，否定 H6。

判定单位是 run；Wilson 区间为 95%，分母为该行全部 n=5（失败 run 仍保留在原始证据中，不伪装成成功）。

## 变体

| 变体 | 唯一改变 |
|---|---|
| V0 | 当前 CLI system guidance 与原始英文 notes 描述。 |
| V1 | guidance 改成回答具体数值前必须先 `note_list` 的命令式前置动作。 |
| V2 | guidance 加入显式记忆模型与一次完整 `note_list → note_read → 回答` 示范。 |
| V3 | 只把 notes 工具描述改成中文，并说明何时使用及不要重跑命令。 |
| V4 | 不生成 sidecar 归档、不向 system prompt 提供归档路径；notes 是唯一找回路径。 |
| V5 | 只在任务提示词中直接点名先调用 `note_list`，作为 sanity check。 |
| V6 | 只增加 runtime final-guard nudge：首次无 notes 的 end-turn 注入指定 user 消息，最多续跑 2 轮。 |

所有变体固定 `budgetTokens=3000`、`keepRounds=2`、`maxRounds=12`、同一任务和三段 `seq` 大输出。随机值只在 JSON 中保存前 4 位和长度。

## 证据解释与归因结论

结果应按“工具是否可见 → 触发是否足够 → 替代路径是否更便宜 → 形态是否影响 → 强制 nudge 是否仍失败”的顺序解释。V5 是最强 sanity check：若 V5 的 notes 调用率接近 100%，工具能力和 schema 通路成立，V0 的 0 率不能归因于 H1/H6，而优先归因 H3/H4/H5；若 V4 在 archive_read 消失后 notes 上升，H4 得到直接支持。V6 若在首次 end-turn 后调用 notes，说明 runtime nudge 可补齐触发缺口；若仍不调用，才有较强证据支持 H6。

本报告的最终排序以本次 JSON 聚合为准：V0: note_call=0/2, archive_read=2/2, value_in_context=0/2, rerun_command=0/2, hit/rerun/invented/noAnswer=0/0/1/1; V1: note_call=1/2, archive_read=2/2, value_in_context=0/2, rerun_command=0/2, hit/rerun/invented/noAnswer=0/0/1/1; V2: note_call=1/2, archive_read=2/2, value_in_context=0/2, rerun_command=0/2, hit/rerun/invented/noAnswer=0/0/0/2; V3: note_call=2/2, archive_read=2/2, value_in_context=0/2, rerun_command=0/2, hit/rerun/invented/noAnswer=0/0/0/2; V4: note_call=2/2, archive_read=0/2, value_in_context=0/2, rerun_command=0/2, hit/rerun/invented/noAnswer=0/0/0/2; V5: note_call=2/2, archive_read=2/2, value_in_context=0/2, rerun_command=0/2, hit/rerun/invented/noAnswer=0/0/0/2; V6: note_call=0/2, archive_read=2/2, value_in_context=0/2, rerun_command=0/2, hit/rerun/invented/noAnswer=0/0/0/2。归因：V5 比 V0 的 notes 调用率上升，否定 H1 的“工具完全不可见/不可用”，并支持 H3 的触发条件不足。 V4 在归档被禁用后 notes 上升且 archive_read 下降，支持 H4 的替代路径竞争。 V3 的中文/when-to-use 描述提高 notes 调用，支持 H5。 V1/V2 的可执行前置动作或记忆模型提高调用率，支持 H3。 V6 的 runtime nudge 仍未带来 notes 调用，支持 H6。 H2 操作性证据：0/14 个 run 在具体作答时真值不在 messages 且出现记忆来源声明。

## 可执行修复建议

首选把 V2 的显式记忆模型和“具体数值回答前先 `note_list`、再 `note_read`”写进 CLI guidance，并采用 V3 的中文、when-to-use 工具描述；这两项成本低、不会改变 loop API，预期收益是提高 notes 触发率并保留模型自主性。对 provenance gate 已经发现未核验具体值的场景，再采用 V6 的一次 runtime nudge（最多 2 轮），作为 fail-closed 的恢复路径；成本是额外模型轮次和 token，不能无限重试。V4 不建议直接产品化：禁用归档会移除另一条可恢复路径，只有在宿主已经提供等价持久笔记且接受单点故障时才适用。

- 每个变体/模型 n=5，Wilson 区间很宽，不能据此估计稳定的生产提升。
- 只有 kimi-for-coding 与 k3；deepseek 当前 token 不可用，未纳入。

## 补充分析（人工复核，2026-09-13）：**工具链断裂** —— 本轮最重要的发现

### 1. 关键事实：调用率上升了，但 **hit = 0/14**

| 变体 | note_call | archive_read | hit | invented | noAnswer |
|---|---|---|---|---|---|
| V0 基线 | 0/2 | 2/2 | 0 | 1 | 1 |
| V1 命令式前置动作 | 1/2 | 2/2 | 0 | 1 | 1 |
| V2 记忆模型+示范 | 1/2 | 2/2 | 0 | 0 | 2 |
| V3 中文工具描述 | **2/2** | 2/2 | 0 | 0 | 2 |
| V4 禁用归档 | **2/2** | 0/2 | 0 | 0 | 2 |
| V5 任务提示点名工具 | **2/2** | 2/2 | 0 | 0 | 2 |
| V6 runtime nudge | 0/2 | 2/2 | 0 | 0 | 2 |

**修正机器结论的归因优先级**：V1/V2/V3/V5 确实提高了"调用率"，但这**不等于任务成功**——**没有一个变体答对过**。因此"H3 触发条件不足 / H5 工具形态不吸引"只解释了*要不要碰工具*，**没有解释*为什么碰了也没用***。

### 2. 真正的原因：**取回链路过长 + 有更短的路**

从 `scripts/notes-why-results.json` 的逐 run 工具调用序列（V3/V4/V5）：

```
V3-kimi : exec,exec,tree,readFile,exec,tree,readFile,note_list,exec,exec,exec,tree,readFile,readFile,readFile
V4-kimi : exec,exec,exec,tree,note_list,rg,note_list,note_list,exec,exec,tree,rg,note_list,note_list,tree,exec,exec,exec
V5-kimi : exec,exec,exec,tree,note_list,tree,readFile,readFile,exec,tree,note_list,exec,tree,readFile,readFile,readFile,readFile
V5-k3   : exec,note_list,exec,tree,readFile,readFile,note_take,exec,note_take,...,note_list,note_take
```

三个事实：
1. **它们会 `note_list`，但几乎从不 `note_read`**（上述 run 中 0 次）——索引看到了，下一步没有发生；
2. **转而去遍历归档目录**（`tree` / `readFile` / `rg` / `exec` 反复读文件），读入大量 `seq` 输出，轮次耗尽 → `noAnswer`；
3. 所有 run 的 `value_in_context_at_answer = false` → 值确实已不在上下文（它们**确实缺信息**）。

**机制层面的原因（设计缺陷，不是模型懒）**：

| 环节 | 现状 | 模型视角 |
|---|---|---|
| `note_list` | 对 artifactRef 类型的笔记，preview 是固定的 `[artifact reference]` | "这条笔记没有任何信息，也不知道该干什么" |
| `note_read` | 返回 `artifactRef`（路径 + digest + locator） | "给了一个路径，我还得再读一次文件" → 链路变成 `list → read → readFile` 三步 |
| 归档目录 | 就在磁盘上、`tree` 一敲就能看见 | **比三步链路更短的替代路径** → 模型走它 |
| 归档内容 | 包含 `seq 1..400` 等大输出 | 无界浏览 → 上下文被垃圾撑满 → 轮次耗尽 |

即：**我们为了安全把笔记做成了"只有引用"，结果把取回变成了一条又长又没信息量的链；而旁边就摆着一条更短（但更容易迷路）的路。模型选了短路，然后迷路了。**

### 3. 对 H2（记忆错觉）的形态修正

`value_in_context=0/14`，但它们**没有**说"我记得"，而是去**搜索**。所以准确表述是：**缺信息时不做定向取回，改做无界探索（exploration）**——这比"记忆错觉"更接近观察：模型缺的是"知道该去哪拿"的**确定性路径**，而不是"不知道自己忘了"。

### 4. H4 得到最强支持

V4（禁用归档）下 `archive_read=0/2`、`note_call=2/2`——**当短路被移走，模型立刻走笔记路线**。说明不是"抗拒笔记工具"，而是**在两条路之间选了更省事的那条**。

### 5. 无 guard 时编造仍会发生

V0/k3、V1/kimi 各 1 次 `invented`——证明 provenance gate（默认开）仍是必要的兜底，不能因为"有了笔记"就撤掉。

## 代码级根因（已于本分支修复）

逐行核对确认，取回链路的第一个断点不在归档，而在 `bin/auto-capture.js` 的 `captureToolExecution()`：`candidateLines(output)` 已经返回 `{label, value}`，但写入 `recordAutoCapture()` 时只传了 `artifactRef`，把手头的短值丢掉了。第二个断点在 `skills/notes/skill.mjs`：`preview()` 对仅引用版本固定返回 `[artifact reference]`，`recordValue()` 又把没有 `content` 的未验证引用降为 `unverified` 并只提示“先核对归档”，因此 `note_list → note_read → readFile` 被代码主动塑造成默认路径。

本分支的修复是：

- 从 notes skill 导出 `NOTE_VALUE_MAX_CHARS = 256`（同时导出已有的 `MAX_CONTENT_LENGTH`），auto-capture 对凭据候选仍整条跳过；短值写入 `content`，并始终保留 `artifactRef` 和 `provenance.verified=false`，超出上限只写引用。
- 有 `content` 的 `note_read` 返回 `status=found`、`value` 和 `artifactRef`；仅引用版本保留 `unverified`，但 `next` 明确给出 `artifactRef.archivePath` 与 `locator` 的有界两步核对说明。
- `note_list` 的值型条目给出值型 preview 和“已有值可直接使用”，引用型条目给出 `note_read key=<key>`；CLI 归档提示也改为先走 `note_list → note_read`，只有仅引用时才读指定 locator。

### e2e 前后对比

修复前的 stage 1 证据是 `hit=0/14`：模型看到引用清单后几乎不调用 `note_read`，转而遍历归档目录。修复后，三次真实 `node bin/cli.js chat`（临时 `kimi-for-coding` 配置、`--compact-budget 3000`、随机 `nonce` + `seq` 大输出）均直接检查到首个笔记文件同时含 `content` 和 `artifactRef`，但真实模型仍未选择 notes 工具，仍出现归档/重跑偏离：run 1 为 `rounds=12`、`final_guard_unverified`；run 2 为 `rounds=12`、`final_guard_unverified`；run 3 为 `rounds=12`、`end_turn` 且命中真值，但工具序列仍包含 `readFile`。因此代码级取回能力已从“值不存在”修复为“一次 `note_read` 可返回值+引用”，但这三次 relay e2e 同时表明模型选择策略仍需独立的提示/调度实验，不能把本修复宣称为已解决所有模型不调用 notes 的行为问题。
